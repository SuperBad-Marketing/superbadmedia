# SuperBad Profile — Source of Truth

**Goal:** A single, living business profile that every LLM-powered feature reads as context — replacing the 14+ hardcoded voice fragments scattered across prompt builders with one canonical document that stays current as the business evolves.

**Date:** 2026-04-28
**Status:** Spec — not yet built. Blocked until Andy gives the go. Instagram autoresponder build session must coordinate with this.

---

## 1. What This Is

The SuperBad Profile is a first-class entity in the platform: a structured, versioned document describing who SuperBad is, what it does, how it sounds, and what makes it different. It has two halves:

1. **Personality half** — SuperBad's own Brand DNA assessment (already supported via `brand_dna_profiles.subject_type = 'superbad_self'`). Generated by the existing Brand DNA pipeline. Produces signal tags, prose portrait, first impression.

2. **Business facts half** — 10 structured sections with auto-generated prose summaries. Stored in a new `business_profile` table. Captures what Brand DNA cannot: services, pricing, audience, positioning, social proof, origin story, current focus, and voice rules.

Every LLM call on the platform receives the appropriate depth of this profile automatically via the invoke layer — no prompt builder has to manually compose SuperBad's identity.

## 4. Tiered Injection via the Invoke Layer

The core architectural change: `invokeLlmText` in `lib/ai/invoke.ts` gains automatic SuperBad identity injection based on model tier.

### 4.1 How it works

```
invokeLlmText({ job, prompt, system?, ... })
  │
  ├── modelTierFor(job) → "opus" | "sonnet" | "haiku"
  │
  ├── loadSuperBadContext(tier) → string
  │     ├── opus:   full prose portrait + all 10 section prose summaries
  │     ├── sonnet: voice rules + design rules (external or internal, matched to job context) + positioning
  │     └── haiku:  tone markers + banned words + colour palette + one-line identity summary
  │
  ├── if caller passed system?: prepend SuperBad context, then caller's system
  │   if no system?: SuperBad context becomes the system message
  │
  └── proceed with API call as before
```

### 4.2 Opt-out mechanism

Some jobs should NOT receive SuperBad identity injection — specifically:

- **Brand DNA assessment generators** (`brand-dna-generate-*`) — these are writing *about* a subject, not *as* SuperBad. Injecting SuperBad's identity would contaminate the portrait.
- **Classification/extraction jobs** (`lead-gen-icp-prefilter`, `inbox-classify-*`, `lead-gen-reply-classify`, `instagram-classify-inbound`, `hiring-candidate-score`) — pure analysis, no voice needed.
- **Internal-only functional jobs** (`finance-draft-narrative`) — these talk to Andy, not clients; voice consistency is nice-to-have, not load-bearing.
- **Parsing/mood jobs** (`braindump-parse`, `braindump-mood-signal`) — these parse Andy's raw text into structured items. No voice generation, just classification. Injecting the profile wastes tokens for zero benefit.

The model registry gains an optional `injectProfile: boolean` flag per job slug (default `true`). Jobs that opt out are listed explicitly:

```typescript

  "brand-dna-generate-prose-portrait",
  "brand-dna-generate-company-blend",
  "brand-dna-generate-retake-comparison",
  "brand-dna-generate-brand-pack",
  // Classification / extraction — pure analysis, no voice
  "intro-funnel-signal-tag-extraction",
  "lead-gen-icp-prefilter",
  "lead-gen-reply-classify",
  "inbox-classify-inbound-route",
  "inbox-classify-notification-priority",
  "inbox-classify-signal-noise",
  "inbox-classify-support-ticket-type",
  "inbox-compose-subject",
  "instagram-classify-inbound",
  "hiring-candidate-score",
  "hiring-archive-reflection-ingest",
  "hiring-reply-classify",
  "drift-check-grader",
  "six-week-plan-review",
  "content-score-keyword-rankability",
  "content-select-visual-template",
  "content-generate-image-prompt",
  "content-match-content-to-prospects",
  // Parsing / internal — no voice generation
  "braindump-parse",
  "braindump-mood-signal",
  "finance-draft-narrative",
  "call-custom-questions",

```

All other jobs automatically receive injection at their tier-appropriate depth. The tier is derived from `modelTierFor(job)` at call time — no per-job configuration needed for injected jobs. When new job slugs are added to the registry, they inherit injection by default unless explicitly added to the exclusion list. The build session reconciles the exclusion list against the live `MODELS` object in `lib/ai/models.ts` as the definitive source of all 53+ job slugs.

### 4.3 Migration path for existing prompt builders

Once the invoke layer handles injection, the 14 prompt builders that currently hardcode voice rules can be simplified:

**Phase 1 (this build):** Add invoke-layer injection. Existing hardcoded voice blocks in prompt builders remain — they'll be redundant but not conflicting, since the profile content matches what's hardcoded.

**Phase 2 (follow-up):** Strip hardcoded voice blocks from prompt builders one by one. Each removal is a small, testable change. The drift checker validates that output quality doesn't regress. This can happen incrementally across future build sessions — it's cleanup, not a prerequisite.

This two-phase approach means the profile feature ships without touching any existing prompt builder. Zero risk of breaking current LLM behaviour.

### 4.4 Caching

`loadSuperBadContext(tier)` caches the assembled context string in memory with a 10-minute TTL (matching the existing API client cache). Profile updates invalidate the cache. This means at most one DB read per 10 minutes across all LLM calls, not one per call.

### 4.5 Prose summary generation

When structured data in a section is created or updated, the prose summary is auto-generated via a Haiku-tier LLM call (new job slug: `profile-generate-prose-summary`). Haiku is sufficient — this is summarisation, not creative writing. The prose is what Opus-tier calls read, but Haiku generates it. If `prose_manually_edited` is `true` for that section, auto-generation is skipped (Andy's hand-written prose is preserved). The "Regenerate prose" button on the profile page overrides this flag and re-generates.

### 4.6 Relationship to `brand_voice_examples`

The outreach system uses a `brand_voice_examples` table storing approved real emails by surface (e.g. `surface = 'outreach'`). These are **output examples** — actual emails Andy approved. The SuperBad profile is **identity description** — who the business is and how it sounds. They serve different purposes and both continue to exist:

- The profile tells the LLM *who to be*
- The voice examples show the LLM *what that looks like in practice*

Outreach draft generation currently loads both (`getSuperbadBrandProfile()` + voice examples query). After this feature ships, the profile injection replaces the `getSuperbadBrandProfile()` call (the invoke layer handles it), but the voice examples query remains unchanged — it's feature-specific context, not platform-wide identity.

### 4.7 Activity logging

All profile mutations are logged to `activity_log`:

| Kind | Trigger |
|---|---|
| `profile_section_created` | First-time section content saved |
| `profile_section_updated` | Section content changed (manual, braindump, or automated) |
| `profile_suggestion_created` | New suggestion generated |
| `profile_suggestion_approved` | Suggestion approved (with resulting section update) |
| `profile_suggestion_dismissed` | Suggestion dismissed by Andy |
| `profile_suggestion_expired` | Suggestion auto-expired after 30 days |
| `profile_prose_regenerated` | Prose summary re-generated from structured data |
| `profile_health_check_run` | Daily health check completed (with summary of findings) |

## 5. Automated Detection

### 5.1 Event triggers

| Event | Source | Suggestion type | Target section |
|---|---|---|---|
| Deal reaches Won stage | Pipeline `finaliseDealAsWon()` | `add` | `social_proof` |
| Trial shoot pricing changes on the website | Cron job comparing `/trial-shoot` page content to `services` section | `mismatch` | `services` |
| SaaS product pricing changes in DB | `products` table update hook | `mismatch` | `services` |
| Case study published | Content Engine publish event | `add` | `social_proof` |
| New service/product created | `products` table insert | `add` | `services` |
| Braindump contains profile-relevant content | Braindump parse step (LLM classification) | varies | varies |
| Quarter changes (Jan/Apr/Jul/Oct) | Cron job on 1st of quarter month | `update` | `current_focus` |
| Brand DNA retaken | `brand_dna_profiles` update for `superbad_self` | `update` | `voice_rules` (prose re-sync) |

### 5.2 Braindump integration

The existing `parseBraindumpAction` LLM call gains an additional output type: `ParsedProfileSuggestion`. When the braindump text contains business identity content ("we're focusing on hospitality this quarter", "just signed Thetford for a retainer", "dropping the Session tier next month"), the parser classifies it and creates a `business_profile_suggestions` row.

The braindump review screen shows profile suggestions as a distinct category alongside tasks, content ideas, and script ideas. Andy approves or dismisses before commit.

### 5.3 Mismatch detection

A scheduled job (`profile_health_check`, daily at 4am Melbourne) runs these checks:

1. **Pricing sync:** For trial shoot pricing, reads from the source data constants in the trial shoot page component (not by rendering the page — reads the data directly). For SaaS pricing, reads from the `products` table via `listActivePricingProducts()`. Compares both to the `services` section structured data. Any mismatch creates a `mismatch` suggestion.
2. **Stale sections:** Any section not updated in 90 days gets flagged as potentially stale (configurable via `settings` key `profile.stale_threshold_days`).
3. **Empty sections:** Any section with no structured data gets flagged.
4. **Brand DNA sync:** If the `superbad_self` Brand DNA profile has been regenerated since the last `voice_rules` prose sync, flag it.

### 5.4 Suggestion expiry

Suggestions older than 30 days (configurable via `settings` key `profile.suggestion_expiry_days`) are auto-dismissed by the `profile_health_check` job with `status = 'expired'`. Prevents the queue from filling with stale suggestions that Andy chose to ignore. Expired suggestions are logged to `activity_log` for audit trail but don't resurface.

The dedicated profile page (`/lite/admin/profile`) shows a visual health summary at the top:

### 6.1 Section health states

| State | Visual | Meaning |
|---|---|---|
| **Complete** | Green indicator | Section has structured data, prose summary, updated within threshold |
| **Stale** | Amber indicator | Section exists but hasn't been updated in >90 days |
| **Mismatch** | Red indicator | Automated detection found a discrepancy with live platform data |
| **Empty** | Grey indicator | Section has no structured data |
| **Pending suggestions** | Badge count | Number of unresolved suggestions targeting this section |

### 6.2 Overall health score

A simple fraction: `complete sections / total sections`. Displayed as a visual progress indicator (not a percentage — percentages feel clinical). Example: "8 of 10 sections current" with the two gaps named.

### 6.3 Health banner integration

Profile health contributes to the cockpit health banner system via `getProfileHealthBanners()`:

- **Critical:** 0 sections complete (profile is empty) AND client-facing LLM calls are being blocked by the tiered enforcement gate.
- **Warning:** Any section has a `mismatch` suggestion. Or 3+ sections are stale.

## 8. Tiered Enforcement

### 8.1 Client-facing LLM calls — blocked without profile

These jobs return a structured error (not a crash) if the business profile has zero complete sections AND no `superbad_self` Brand DNA exists:

- All outreach draft jobs (`lead-gen-outreach-draft`, `lead-gen-nudge-rewrite`, `lead-gen-reply-draft`, etc.)
- All client-facing email drafts (`invoice-draft-send-email`, `quote-builder-draft-send-email`, `onboarding-welcome-email`, etc.)
- Portal bartender (`client-mgmt-chat-response`, `client-mgmt-bartender-opening-line`)
- Content generation (`content-generate-blog-post`, `content-studio-generate-copy`, etc.)
- Instagram responses (`instagram-draft-comment-reply`, `instagram-draft-dm-reply`)
- Six-week plan generation (`six-week-plan-strategy`, `six-week-plan-weeks`)

The error surfaces as a health banner: "SuperBad profile incomplete — client-facing AI is paused."

### 8.2 Admin-only LLM calls — degrade gracefully

These jobs proceed without the profile, using the existing `FALLBACK_SUPERBAD_PROFILE` constant as a minimal stand-in:

- Cockpit briefs (`cockpit-brief`)
- Braindump parsing (`braindump-parse`)
- Admin assistant (`admin-setup-assistant`, `cockpit-assistant`)
- Internal classification jobs
- Hiring jobs

A health banner warns: "SuperBad profile incomplete — admin AI using fallback voice."

### 8.3 Kill switch

`profile.enforcement_enabled` (default: `true`). When disabled, all jobs fall back to the existing behaviour (hardcoded prompt fragments / `FALLBACK_SUPERBAD_PROFILE`). This is the escape hatch if the profile feature has a bug — the platform reverts to exactly how it works today.

**Partial saves are fine.** Andy can fill out Identity and Services in one sitting and come back for the rest later. Each section saves independently. The profile health snapshot shows exactly what's done and what's still empty. The tiered enforcement (§8) only blocks client-facing calls when the profile has *zero* complete sections AND no Brand DNA — filling out even one or two sections plus having Brand DNA is enough to unblock everything.

## 13. Dev-Time Access (Claude Code)

The profile isn't just a runtime document for LLM calls — it's also the reference Claude Code should read when building new features or creating external assets.

### 13.1 Exported snapshot file

On every profile update, a static snapshot is written to `docs/superbad-profile-snapshot.md` — a human-readable markdown rendering of the full profile (all 10 sections + Brand DNA summary). This file is:

- **Checked into git** — always present in the working directory
- **Referenced in CLAUDE.md** — so every Claude Code session knows it exists
- **Read by build sessions** — any session building UI or client-facing features reads this file as part of its preconditions, alongside the feature spec

This means Claude Code doesn't need DB access to know the design rules, voice rules, or brand positioning. The snapshot is the dev-time equivalent of the runtime profile injection.

### 13.2 What the snapshot contains

The snapshot renders each section as a headed block: Brand DNA (personality), Identity, Services, External Design Rules, Internal Design Rules, Voice Rules, Audience, Positioning, Current Focus, Social Proof, Origin Story. Each block contains the prose summary followed by the key structured fields. External and Internal Design Rules include all structured fields in full (colours, typography, composition rules, motion tokens, etc.) since these are the fields Claude Code needs verbatim during build sessions.

### 13.3 CLAUDE.md addition

When this feature ships, CLAUDE.md gains a line:

> **SuperBad Profile:** Read `docs/superbad-profile-snapshot.md` before any UI build session or client-facing content work. This is the canonical source for design rules, voice, and brand identity.

### 13.4 Keeping the snapshot current

The snapshot regenerates automatically whenever any section is updated (manual edit, approved suggestion, or Brand DNA retake). It's a derived artefact — the database is the source of truth, the snapshot is a convenience export. If the snapshot is stale (older than the most recent `updated_at_ms` across all sections), the profile health check flags it and regenerates.

## 18. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Token cost increase from injecting profile into every call | Higher Anthropic spend, especially on Haiku calls | Tiered injection keeps Haiku context minimal (~50 tokens). Cache prevents repeated DB reads. Monitor via Observatory. |
| Profile content quality affects all LLM output simultaneously | Bad prose in one section degrades every feature | Profile changes require explicit approval. Drift checker validates output. Kill switch reverts to pre-profile behaviour. |
| Invoke-layer change breaks existing LLM calls | Widespread regression | Phase 1 adds injection without removing existing hardcoded context. Both coexist. Phase 2 removes redundancy only after validation. |
| Stale profile worse than no profile | LLM confidently states outdated facts | Automated detection catches common staleness (pricing, quarter changes). Health banners make staleness visible. 90-day stale threshold is configurable. |
| Instagram autoresponder build session conflicts | Schema or injection changes collide | This spec's invoke-layer injection is the only shared seam. Autoresponder session reads from it, doesn't write to it. Dependency is one-directional. |
