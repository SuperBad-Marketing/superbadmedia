Section 01

What the Billing System Does

SuperBad Lite has two revenue arms that share the same underlying Stripe primitives but reach customers through completely different paths:

  • Retainer arm (Quote Builder): Andy builds a custom quote for a client. Client accepts. A Stripe Subscription is created. Monthly invoices auto-generate. Commitment is enforced at the Lite UX layer, not by Stripe.
  • SaaS arm (Subscription Billing): Subscribers self-serve through a public checkout. They pick a product, tier, and commitment length. A Stripe Subscription is created. Usage limits are enforced per billing cycle.

Both arms converge on the same deals table for subscription state, the same cancel flow at /lite/portal/subscription, the same scheduled_tasks worker for lifecycle events, and the same webhook_events idempotency table for Stripe event processing.

The billing system also handles: branded invoice generation with ATO-compliant PDFs, a full finance dashboard with P&L and tax provisioning, expense tracking, and accountant-ready export bundles.

Two revenue arms. One Stripe SDK. Zero spreadsheets.

Section 02

Architecture

Stripe Integration Pattern

Stripe is accessed exclusively through lib/stripe/. Feature code never imports the Stripe SDK directly — an ESLint rule (no-direct-stripe-customer-create) enforces the boundary. The SDK singleton is lazy-initialised via getStripe() to avoid build-time crashes when environment variables are absent.

lib/stripe/client.ts — Lazy Singleton
import Stripe from "stripe";

const globalForStripe = globalThis as unknown as { _stripe?: Stripe };

export function getStripe(): Stripe {
  if (globalForStripe._stripe) return globalForStripe._stripe;
  const instance = new Stripe(process.env.STRIPE_SECRET_KEY ?? "", {
    apiVersion: "2026-03-25.dahlia",
    typescript: true,
  });
  if (process.env.NODE_ENV !== "production") {
    globalForStripe._stripe = instance;
  }
  return instance;
}

Subscription Management

Pricing Philosophy — Popcorn Pricing

The pricing model deliberately avoids discounts. Same per-month price for monthly and annual. Monthly includes a one-time setup fee. Annual waives it. The framing is identity and commitment, not bargain-hunting.

CommitmentMonthly RateSetup FeeIdentity Frame
Monthly$X/moYes (one-time)“Getting started”
Annual (monthly-billed)$X/moWaived“Committed”
Annual (upfront)$X × 12 todayWaived“All in”

Stripe Object Mapping

On product publish, syncProductToStripe() creates one Stripe Product per Lite product. Then syncTierPricesToStripe() creates three Stripe Prices per tier:

  • Monthly recurring — interval: 'month'
  • Annual monthly-billed — interval: 'month' (commitment enforced by Lite, not Stripe)
  • Annual upfront — interval: 'year'

Prices are immutable in Stripe. Price changes archive the old Price and create a new one. Existing subscribers stay on their current Price until renewal or explicit tier change.

Setup Fee Mechanics

The setup fee is the only place in the codebase that constructs an add_invoice_items payload. A grep-guard test (tests/billing/setup-fee-guard.test.ts) fails if any other file references the literal. The setup fee on every new monthly subscription naturally closes the cancel-and-resubscribe-cheaper loophole.

lib/billing/setup-fee.ts — Core Logic
export function buildMonthlySetupFeeInvoiceItems(
  params: BuildSetupFeeParams
): Pick<Stripe.SubscriptionCreateParams, "add_invoice_items"> | undefined {
  if (params.cadence !== "monthly") return undefined;
  if (params.setupFeeCentsIncGst <= 0) return undefined;
  return {
    add_invoice_items: [{
      price_data: {
        currency: "aud",
        product: params.stripeProductId,
        unit_amount: params.setupFeeCentsIncGst,
      },
      quantity: 1,
    }],
  };
}

Cancel Flow

The cancel flow lives at /lite/portal/subscription and branches based on whether the subscriber is within their commitment period:

  • Pre-term retainer: “Let’s chat” (no charge), pay remainder, 50% buyout
  • Pre-term SaaS: pay remainder, 1-month pause (one per commitment), continue
  • Post-term: upgrade, downgrade, or cancel with “here’s what you’d be losing”

Paid exits use off-session Payment Intents via createOffSessionPaymentIntent() with idempotency keys scoped to saas_exit:{deal_id}:{branch}:{today_iso}.

Invoice System

What It Handles

Branded Invoicing serves manual-billed companies only — clients whose companies.billing_mode = 'manual'. Stripe-billed clients receive native Stripe invoices. SaaS subscribers have their own billing flow.

Invoice Number Format

SB-INV-YYYY-NNNN (e.g. SB-INV-2026-0001). Year-scoped sequence allocated atomically via the shared sequences table using upsert + increment.

lib/invoicing/sequences.ts
export async function allocateInvoiceNumber(opts) {
  const rows = await db
    .insert(sequences)
    .values({ name: sequenceName(year), current_value: 1 })
    .onConflictDoUpdate({
      target: sequences.name,
      set: { current_value: sql`${sequences.current_value} + 1` },
    })
    .returning({ value: sequences.current_value });
  return formatInvoiceNumber(year, rows[0].value);
}

Two-Step Generation Primitive

  1. generateInvoice() — Creates the invoice in draft status. Copies recurring line items from the accepted quote. Derives GST. Allocates invoice number.
  2. sendInvoice() — Renders PDF via Puppeteer, drafts a Claude-generated email (drift-checked against Brand DNA), dispatches via sendEmail(), transitions to sent.

Payment Methods

  • Bank transfer (primary for manual-billed clients) — Andy clicks “Mark as paid” when the deposit clears
  • Stripe online — inline Payment Element on the invoice web view. Payment Intent metadata tags product_type: "invoice" and invoice_id for webhook matching

Supersede Pattern (Edit After Send)

A sent quote is immutable. To edit it, Andy creates a new row with supersedes_quote_id pointing to the original. The original is voided. The old URL shows a redirect card. This pattern is reused by Branded Invoicing for invoice corrections.

Line Item Projection

The projectCycleLineItems() function in lib/invoicing/generate.ts maps quote content to invoice line items. Cycle 0 carries both retainer and one-off items. All subsequent cycles carry only retainer items.

Section 06

One-Off Payments

Three Contexts for One-Off Charges

1. Intro Funnel — Trial Shoot Payment

The intro_funnel_payments table tracks payments for trial shoots. Uses a standard Stripe Checkout Session with metadata.product_type = "intro". On success, the webhook calls markCompanyTrialShootBooked().

2. Invoice Online Payment

Manual-billed invoices offer an inline Stripe Payment Element on the web view (/lite/invoices/[token]). A Payment Intent is created with metadata.product_type = "invoice" and metadata.invoice_id. On success, markInvoicePaid() flips the invoice to paid.

3. Cancel-Flow Paid Exits

Pre-term cancellation options (pay remainder, 50% buyout) use off-session Payment Intents charged against the customer’s default payment method. No card re-entry required.

lib/stripe/payment-intents.ts — Off-Session Pattern
export async function createOffSessionPaymentIntent(
  opts: CreateOffSessionPaymentIntentOpts,
): Promise<Stripe.PaymentIntent> {
  const customer = await stripe.customers.retrieve(opts.stripeCustomerId);
  const defaultPm = customer.invoice_settings?.default_payment_method;
  if (!defaultPm)
    throw new OffSessionPaymentError("no_default_payment_method", ...);

  return stripe.paymentIntents.create(
    {
      customer: opts.stripeCustomerId,
      amount: opts.amountCents,
      currency: opts.currency ?? "aud",
      payment_method: defaultPm,
      off_session: true,
      confirm: true,
      metadata: opts.metadata,
    },
    { idempotencyKey: opts.idempotencyKey },
  );
}

Section 07

Stripe Webhook Handler

Entry Point

app/api/stripe/webhook/route.ts receives POST requests, verifies the stripe-signature header, and dispatches to dispatchStripeEvent(). The route always responds 200 — even when dispatch returns error or skipped. Triage happens off the webhook_events table, not via Stripe retries.

Idempotency Strategy

Every event is written to webhook_events before dispatch. The primary key is the Stripe event ID. Events that previously completed with "ok" are skipped. Events that previously errored or were skipped can be reprocessed on resend — this prevents “stuck” events that failed once and can never retry.

Kill Switch

The setting pipeline.stripe_webhook_dispatch_enabled gates all dispatch. When false, every event returns skipped:kill_switch without touching the CRM. Useful for maintenance windows.

Events Handled

EventHandlerEffect
checkout.session.completed handleCheckoutSessionCompleted Routes by metadata.product_type: “intro” books trial shoot, “retainer”/“saas” finalises deal as Won
payment_intent.succeeded handlePaymentIntentSucceeded “quote”: creates Subscription, finalises deal, sends settle email. “invoice”: flips invoice to paid
payment_intent.payment_failed handlePaymentIntentFailed Audit log only. Quote stays accepted. Invoice stays sent/overdue. Client retries in the Payment Element.
invoice.payment_succeeded handleInvoicePaymentSucceeded Recovers from past_due: resets failure counter, flips to active_current, cancels pending data-loss warning. Issues initial subscriber login link for new SaaS subs.
invoice.payment_failed handleInvoicePaymentFailed Flips to past_due, increments failure counter. First failure: enqueues saas_data_loss_warning scheduled task. Emits admin event + regenerates cockpit brief.
customer.subscription.updated handleSubscriptionUpdated Maps Stripe status to deals.subscription_state. Idempotent — no-op when state already matches.
customer.subscription.deleted handleSubscriptionDeleted Audit log only. The cancel flow owns state authoritatively — this webhook is the confirmation handshake.

Payment Failure Escalation

invoice.payment_failed (1st failure)
  → subscription_state → past_due
  → failure counter = 1
  → enqueue saas_data_loss_warning (fires in N days)
  → admin event emitted
  → cockpit brief regenerated

invoice.payment_failed (2nd, 3rd failure)
  → counter incremented only

invoice.payment_succeeded (recovery)
  → state → active_current
  → counter reset to 0
  → pending data-loss task cancelled
Section 08

GST & Tax Handling

Core Principle: Felt Experience Wins

Every amount in the system is stored GST-inclusive in integer cents. This is the “felt” number — what the customer sees and what Andy thinks in. Convention-compliant values (ex-GST, GST line items) are derived at compliance boundaries: tax invoices, BAS exports, EOFY bundles.

The Rule

When convention and felt experience conflict, felt experience wins unless compliance forces the convention. Store the felt value. Derive the conventional value at the boundary.

GST Derivation

GST Calculation Logic
// For GST-applicable companies (standard 10% GST):
total_cents_ex_gst  = Math.round(total_cents_inc_gst / 1.1)
gst_cents           = total_cents_inc_gst - total_cents_ex_gst

// For non-GST-applicable companies:
total_cents_ex_gst  = total_cents_inc_gst
gst_cents           = 0

GST Applicability

Tracked per company via companies.gst_applicable (boolean, default true). Snapshotted onto each invoice at generation time via invoices.gst_applicable, so a later change to the company record does not retroactively affect existing invoices.

ATO Compliance on Invoices

Invoice PDFs include all ATO requirements: “Tax Invoice” title, invoice number, issue/due dates, supplier ABN, billed-to block, itemised GST, and the GST-inclusive total. When gst_applicable = false, the GST line is omitted with a “GST not applicable” note.

Tax Provisioning (Finance Dashboard)

The finance dashboard calculates two provisions from settings:

  • GST owed this quarter: GST collected on paid invoices minus GST paid on confirmed expenses
  • Income tax provisioned: net profit YTD × finance.income_tax_rate (default 0.25)

These are estimates, not accounting outputs. The accountant is authoritative at EOFY. The “yours to spend” figure (Stripe balance minus provisions) surfaces a dry callout in the narrative when it drops below one month of average expenses.

SaaS Tier Management

The Popcorn Model

Three tiers per product. The gap between medium and large is deliberately small in price relative to the value increase — the “popcorn effect.” Across products, the Full Suite is priced so subscribing to 2+ individual products is obviously more expensive.

Tier RankName ConventionPurpose
1 (small)Capture tierLow price, enough to start. Gets people in the door.
2 (medium)Default tierWhere most subscribers land. The “sensible” choice.
3 (large)Revenue lift tierSmall price jump from medium, significant limits increase. The no-brainer upgrade.

Product → Tier → Dimension → Limit Hierarchy

saas_products

Usage Tracking Primitives

Two functions in lib/billing/:

Usage Enforcement API
// Call BEFORE a capped action
const { allowed, used, limit, nextTier } =
  await checkUsageLimit(contactId, productId, dimensionKey);

if (!allowed) {
  // Show upgrade prompt with nextTier info
  return;
}

// Execute the action, then:
await recordUsage(contactId, productId, dimensionKey);

Usage resets with each billing cycle. New cycle = new billing_period_start_ms = counter effectively resets. Old records persist for analytics.

Hard Cap with Upgrade Prompt

When checkUsageLimit() returns allowed: false:

  1. Capped action blocked — feature button disabled
  2. Upgrade prompt renders inline with current usage, next tier limits, and pro-rated price
  3. One-click upgrade triggers immediate tier swap via swapSubscriptionPrice({ mode: "immediate" })
  4. If already on highest tier: “you’ve maxed out” message with support link

Stripe Product Sync

syncProductToStripe() creates one Stripe Product per Lite product. syncTierPricesToStripe() creates three Prices per tier. Each Price carries metadata.lite_tier_id and metadata.cadence for traceability. Price changes always create new Price objects and archive old ones — Stripe Prices are immutable.

Tier Limits Protect Margin

Negative margin at small or medium tiers is a tier-design bug, not a subscriber problem. Only top-tier power users warrant per-subscriber triage. The limit_value = null (unlimited) option is reserved for the large tier’s least-expensive dimensions.

Section 12

Implementation Tips

  1. Start with the webhook handler. Everything downstream depends on reliable event processing. Get webhook_events idempotency, signature verification, and the dispatch switch working first. Test with Stripe CLI forwarding.
  2. Every monetary value is integer cents, GST-inclusive. Never store dollars. Never store floats. Derive ex-GST at the compliance boundary only. The deriveInvoiceTotals() helper in lib/invoicing/totals.ts does this in one place.
  3. Idempotency keys are non-negotiable. Every Stripe-mutating call carries one. Every webhook handler checks the webhook_events table first. Every scheduled task has a deterministic key. Double-run of anything should be a no-op.
  4. Never import Stripe directly in feature code. Everything goes through lib/stripe/. The ESLint rule no-direct-stripe-customer-create enforces this. The grep-guard test for setup fees ensures add_invoice_items only appears in one file.
  5. Stripe Prices are immutable. Price changes always create a new Price and archive the old one. The archiveTierPrices() + syncTierPricesToStripe() pattern handles this. Existing subscribers continue on their current Price.
  6. State machine transitions assert the current state. Both transitionInvoiceStatus() and transitionQuoteStatus() use WHERE clauses that check current status. This prevents concurrent callers from corrupting state. If the row count is 0 after the update, the transition was illegal or already happened.
  7. The scheduled-tasks worker is shared infrastructure. It polls every minute, reclaims stale rows after 15 minutes, and retries with exponential backoff. Your billing handler should return { ok: true } or { ok: false, error, retry }. Never throw from a handler.
  8. Setup fee logic lives in exactly one file. lib/billing/setup-fee.ts is the only place that builds add_invoice_items. Callers spread the result into their subscription create params. This constraint is test-enforced.
  9. The cancel flow is UX-layer enforcement, not Stripe-layer. Stripe sees a plain rolling subscription. Lite tracks committed_until_date_ms and routes the cancel flow through pre-term or post-term branches. This keeps Stripe simple and gives full control over the exit experience.
  10. Test payment failure recovery end-to-end. The past_due → active_current path touches multiple handlers: invoice.payment_failed sets the state, invoice.payment_succeeded clears it, and the pending saas_data_loss_warning task gets cancelled. Simulate this full cycle with Stripe CLI test clocks.
  11. The webhook route always returns 200. Never let a dispatch failure cause a non-2xx response. Stripe retries on non-2xx are worse than a recorded failure. Triage happens off the webhook_events table.
  12. All email sends go through sendEmail() with classification: 'transactional'. Billing emails bypass the quiet window. Invoice send, reminder, supersede notification, payment confirmation — all transactional. Never queue billing-critical emails behind a marketing cadence.
Final Note

The billing system has two kinds of bugs: the kind where someone sees the wrong number on a screen, and the kind where someone gets charged twice. Every idempotency key, every state machine assertion, every webhook_events check exists to prevent the second kind. Guard them.
