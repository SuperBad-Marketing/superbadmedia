Section 01

What the AI Infrastructure Does

SuperBad Lite is a SaaS operations platform that runs 115 distinct LLM jobs across 20+ features — everything from drafting outreach emails to generating brand personality portraits to classifying inbound support tickets. Every single one of those calls flows through a centralised AI layer: three files that sit between feature code and the Anthropic API.

The core design principle is feature code never knows which model it’s calling. A quote builder asks for quote-builder-draft-intro-paragraph. A Brand DNA generator asks for brand-dna-generate-prose-portrait. The AI layer resolves the model, makes the call, logs the cost, and returns the text. Feature code doesn’t import the SDK. Feature code doesn’t reference claude-opus-4-6. Feature code names the job.

This matters because model IDs change. Pricing changes. You might want to downgrade a Haiku job to a cheaper tier, or upgrade a Sonnet job to Opus because the output quality isn’t good enough. With a centralised registry, that’s a one-line change in one file. Without it, you’re grepping through 115 call sites.

The boring architecture that lets you sleep at night.

Section 02

Architecture

The Three-File Core

Feature Code
    │
    │  calls invokeLlmText({ job: "job-slug", prompt, maxTokens })
    │
    ▼
lib/ai/invoke.ts           ← single SDK entry point
    │
    │  calls modelFor("job-slug") → "claude-opus-4-6"
    │
    ▼
lib/ai/models.ts          ← model registry (115 job slugs → model IDs)
    │
    │  after response, fires logExternalCall()
    │
    ▼
lib/observatory/          ← cost logging + anomaly detection
    │
    ▼
external_call_log table   ← every call recorded with cost estimate

Data Flow for a Typical LLM Call

1. Feature builds prompt using a prompt builder from lib/ai/prompts/
2. Feature calls invokeLlmText({ job, prompt, maxTokens })
3. invoke.ts resolves API key (DB-stored > env var fallback)
4. invoke.ts calls modelFor(job) → concrete model ID
5. invoke.ts calls Anthropic messages.create()
6. Response arrives → extract text, extract token usage
7. logExternalCall() fires (async, fire-and-forget)
8. Cost estimate computed via estimateAnthropicCostAud()
9. Anomaly detectors check per-call thresholds
10. Text returned to feature code

Enforcement

A custom ESLint rule — lite/no-direct-anthropic-import — blocks any file outside lib/ai/ from importing @anthropic-ai/sdk. If a developer tries to bypass the registry and call Anthropic directly from feature code, the linter catches it.

Section 03

Model Registry

The registry lives in lib/ai/models.ts. It’s a single MODELS object mapping 115 job slugs to one of three tiers: Opus, Sonnet, or Haiku. The concrete model IDs are resolved through a separate MODEL_IDS constant.

lib/ai/models.ts — Core Types
export type ModelTier = "opus" | "sonnet" | "haiku";

export const MODEL_IDS = {
  opus:   "claude-opus-4-6",
  sonnet: "claude-sonnet-4-6",
  haiku:  "claude-haiku-4-5-20251001",
} as const;

export function modelFor(job: ModelJobSlug): ModelId {
  return MODEL_IDS[MODELS[job]];
}

Section 04

Invocation Entry Point

lib/ai/invoke.ts is the only file in the entire codebase that calls Anthropic.messages.create() for feature work. It exports three functions, each serving a different response shape:

FunctionReturnsWhen to Use
invokeLlmTextstringMost jobs — you just want the text output
invokeLlmTextWithMeta{ text, inputTokens, outputTokens }When the caller needs token counts (e.g. showing cost)
invokeLlmVision{ text, inputTokens, outputTokens }When the prompt includes images (e.g. portfolio ingest)

The Options Object

TypeScript — InvokeLlmTextOptions
export interface InvokeLlmTextOptions {
  job: ModelJobSlug;          // registry key, never a model ID
  prompt: string;              // user message content
  system?: string;             // optional system message
  maxTokens: number;           // output cap
  actorType?: "internal" | "external" | "shared" | "prospect";
  actorId?: string | null;    // links cost to a specific entity
}

API Key Resolution

The client resolves the API key through a two-tier fallback:

  1. Database first: Queries integration_connections for an active anthropic row. The key is stored encrypted via the vault module and decrypted at runtime.
  2. Env var fallback: If the DB lookup fails (or the table is empty), falls back to process.env.ANTHROPIC_API_KEY. This is the local dev path.

The resolved client is cached for 5 minutes to avoid hitting the DB on every call.

How a Feature Call Looks

Typical Usage
import { invokeLlmText } from "@/lib/ai/invoke";

const text = await invokeLlmText({
  job: "brand-dna-generate-section-insight",
  prompt: buildSectionInsightPrompt(input),
  maxTokens: 400,
  actorType: "external",
  actorId: profileId,
});

That’s it. The feature doesn’t know it’s calling Opus. It doesn’t know the model ID. It doesn’t handle cost logging. All of that is the invoke layer’s responsibility.

The Prompt Builder Pattern

Every prompt file exports three things:

  1. An input type — a TypeScript interface declaring exactly what context the prompt needs.
  2. An output type (optional) — the shape of the expected JSON response, if the prompt requests structured output.
  3. A builder function — takes the input, returns the complete prompt string.
Anatomy of a Prompt Builder
// 1. Typed input
export type SectionInsightInput = {
  subjectName: string;
  sectionNumber: 1 | 2 | 3 | 4;
  topTags: string;
  answerTraces: AnswerTrace[];
  priorInsights: string[];
  track: string;
};

// 2. Builder function
export function buildSectionInsightPrompt(
  input: SectionInsightInput
): string {
  // Composes the full prompt from input fields
  // Includes voice constraints, structural rules, output format
  return `You're revealing the brand DNA of ${input.subjectName}...`;
}

Key Conventions

  • Prompts never name the model. That’s the registry’s job. The builder outputs a string; the caller passes it to invokeLlmText with a job slug.
  • Spec prose describes intent; prompt files have the actual text. If the spec says “generate an email”, the prompt file contains the exact system instructions, voice constraints, banned words, output format.
  • INDEX.md is the discovery entry point. It lists every prompt with its job slug, owning spec, model tier, and one-line intent. Start there when looking for something.
  • Voice constraints are non-negotiable. Most prompts include explicit banned phrases (“I notice”, “it seems like”, “synergy”, “leverage”), sentence structure rules, and audience context.

Prompt Scope by Feature

Some prompts are massive (the Brand DNA prose portrait prompt runs hundreds of lines with detailed voice calibration). Others are tight templates (the invoice supersede notification is a short Haiku classification). The complexity scales with the tier — Opus prompts tend to be longer and more carefully voice-tuned because the stakes and cost are higher.

Non-Prompt Features

Four specs have no LLM prompts at all: sales-pipeline, saas-subscription-billing, hiring-pipeline (the pipeline itself; hiring discovery has prompts), and design-system-baseline. Everything they do is deterministic.

Section 06

Cost Logging

Every external API call — not just LLM calls, but Stripe, Resend, Twilio, SerpAPI, everything — is logged to the external_call_log table. This powers the Cost & Usage Observatory, which gives the admin real-time visibility into what the platform is spending.

How It Works

invokeLlmText() completes
    │
    ▼
logCost() fires (fire-and-forget)
    │
    ├── Computes estimateAnthropicCostAud(tier, { inputTokens, outputTokens })
    │
    ├── Calls logExternalCall({ job, actorType, actorId, units, estimatedCostAud })
    │       │
    │       ├── INSERT into external_call_log
    │       │
    │       ├── Check: is job registered? If not → cost_anomaly created
    │       │
    │       └── checkPerCallThreshold() → anomaly if cost exceeds ceiling
    │
    └── Never blocks the response. Never throws on insert failure.

Cost Estimation

Cost estimates use hardcoded Anthropic rate-card pricing with a static USD → AUD multiplier (1.55). Accuracy target: ±15%.

TierInput (per M tokens)Output (per M tokens)
Opus$15 USD$75 USD
Sonnet$3 USD$15 USD
Haiku$0.80 USD$4 USD

Actor Attribution

Every logged call carries an actorType that classifies who triggered the cost:

  • internal — Andy or the system (admin operations, cockpit briefs)
  • external — a specific client (their Brand DNA, their portal chat)
  • shared — operations that benefit multiple entities (newsletter generation)
  • prospect — a lead-gen or outreach target (not yet a paying client)

This distinction is critical for the Observatory’s per-subscriber margin calculations. If a single SaaS subscriber is generating excessive LLM costs, the system can detect negative margin at the subscriber level.

Section 07

Brand Voice Drift Checking

Before the platform sends any AI-drafted email on behalf of a client, it runs the draft through a brand-voice consistency checker. This is a Haiku-tier call that scores how well the draft matches the client’s Brand DNA profile.

How It Works

Draft email generated (Opus)
    │
    ▼
checkBrandVoiceDrift(draftText, brandDnaProfile)
    │
    ├── Check kill switches: llm_calls_enabled AND drift_check_enabled
    │   (if either is off → { pass: true, score: 1.0, notes: "skipped" })
    │
    ├── Read threshold from settings: email.drift_check_threshold (default 0.7)
    │
    ├── Build prompt: brand profile + draft → Haiku scores 0.0–1.0
    │
    └── Return { pass, score, notes }
         pass = score ≥ threshold

The Brand DNA Profile Input

TypeScript — BrandDnaProfile
export interface BrandDnaProfile {
  voiceDescription: string;   // "dry, direct, Melbourne wit"
  toneMarkers: string[];      // single words / short phrases
  avoidWords?: string[];      // words the brand explicitly avoids
  targetAudience?: string;   // audience descriptor for context
}

The Return Value

TypeScript — DriftCheckResult
export interface DriftCheckResult {
  pass: boolean;       // true when score ≥ threshold
  score: number;       // 0.0 (severe drift) to 1.0 (perfect match)
  notes?: string;      // one-sentence explanation from the grader
}

When a draft fails the drift check, the calling feature can regenerate with adjusted constraints. The threshold (default 0.7) is configurable via the settings table so it can be tuned without a code change.

Two Kill Switches

The drift checker is gated by both llm_calls_enabled (global) and drift_check_enabled (specific). This means you can turn off drift checking without disabling all LLM calls, or disable all LLM calls and drift checking follows. Belt and braces.

Section 08

Model Tiers — When to Use What

The tier decision for each job was made based on three factors: output quality requirements, latency sensitivity, and cost. Here’s the thinking:

Opus (48 jobs) — The Heavy Hitter

  • Creative writing — Brand DNA portraits, outreach emails, blog posts, talking-head scripts. Anything where voice quality directly affects user perception.
  • High-stakes reasoning — Retainer-fit recommendations, cost anomaly diagnosis, six-week marketing strategy generation. Decisions that have real business consequences.
  • Context-heavy synthesis — Jobs that ingest large amounts of context (Brand DNA tags + answer traces + prior insights + business context) and need to produce coherent narrative from it.
  • Client-facing prose — Quote intro paragraphs, welcome emails, invoice cover letters. Anything that goes in front of a client with the SuperBad name on it.

Sonnet (14 jobs) — The Middle Ground

  • Structured parsing — Braindump parsing (freeform text → structured tasks + content ideas + scripts). Needs to be smarter than classification but doesn’t need Opus-level prose.
  • Mid-complexity drafts — Instagram captions, DM replies, content studio copy. Good enough that the admin won’t need to rewrite, but not mission-critical prose.
  • Hiring intelligence — Discovery agent, portfolio vision analysis, brief synthesis. Multi-step reasoning at moderate cost.
  • Internal assistants — The cockpit assistant (tool-calling chat) uses Sonnet because it needs reliable tool use but the prose quality bar is lower than client-facing work.

Haiku (53 jobs) — The Workhorse

  • Classification — Inbound routing, notification priority, signal/noise filtering, support ticket typing, reply classification. Binary or categorical decisions.
  • Short templates — Scope summaries, subject lines, supersede notifications, abandon emails. Tight-format outputs where the template does most of the work.
  • Reformatting — Channel reformatting (email → SMS), newsletter rewrites from blog posts. The content exists; it just needs reshaping.
  • High-volume pipelines — Keyword rankability scoring, content-to-prospect matching, ICP prefiltering. Jobs that run dozens of times per day where latency and cost compound.
The Upgrade Path

If a Haiku job is producing poor results, promote it to Sonnet by changing one word in models.ts. If a Sonnet job needs better prose, promote to Opus. The feature code doesn’t change at all. This is the whole point of the registry pattern.

Section 09

Kill Switches

Every feature that can spend money, send email, or hit an external API is gated by a kill switch. Kill switches live in lib/kill-switches.ts as a typed registry with boolean defaults. All switches ship disabled at v1.0 and are explicitly enabled during launch.

LLM-Relevant Kill Switches

SwitchDefaultWhat It Gates
llm_calls_enabledtrueGlobal gate for all Anthropic API calls. When off, generators return stub text.
drift_check_enabledfalseBrand-voice drift grader specifically. Can be off while LLM calls are on.
brand_dna_assessment_enabledtrueThe entire Brand DNA assessment flow (includes its LLM generators).
cockpit_briefs_enabledtrueDaily cockpit Opus brief generation.
lead_gen_enabledtrueAll lead-gen LLM jobs (outreach drafts, ICP filtering, reply classification).

Override Mechanisms

Two ways to override defaults without a rebuild:

  1. Environment variable: KILL_SWITCHES_ON=llm_calls_enabled,drift_check_enabled — comma-separated list of switches to force on at process boot. Used for Playwright tests and dev workflows.
  2. Runtime proxy: The exported killSwitches object is writable, so test code can toggle switches directly. Production enablement will come from a DB-backed path.

There are 27 kill switches total across the platform, covering not just LLM calls but email sending, Stripe operations, inbox sync, onboarding nudges, and more. The LLM-relevant subset is above.

Section 11

Error Handling & Anomaly Detection

Invocation Errors

The invoke layer does not retry or catch Anthropic API errors. If the API call throws, the exception propagates to the feature code. This is deliberate — each feature has different requirements for how to handle failure:

  • Brand DNA insight generation — can show a “generation unavailable” state and retry on next page load.
  • Outreach draft — surfaces the error to the admin for manual intervention.
  • Classification — may have a deterministic fallback (e.g. default to "other" ticket type).

The invoke layer’s responsibility is narrow: resolve the model, make the call, log the cost. Error handling is the feature’s problem.

Cost Logging Failures

Cost logging is fire-and-forget. The logCost call uses .catch(() => {}) — if the insert fails (DB unavailable, schema mismatch, whatever), the response still returns to the feature. You never lose an LLM response because the logging layer broke.

Unregistered Job Trap

If a call logs a job slug that isn’t in the Observatory’s job registry, two things happen:

  1. In development: Hard throw. Forces the developer to register the job before shipping.
  2. In production: The log insert succeeds (never lose data), but a synthetic tier: severe cost anomaly is created. The admin sees it immediately in the Observatory.

Three Anomaly Detectors

The Cost & Usage Observatory runs three detectors against the external_call_log data:

DetectorMechanismWhen It Fires
Hard Threshold Compares each call’s cost against the job’s per_call_ceiling_aud, and daily aggregates against daily_ceiling_aud Sync (per-call check) + 5-min sweep (daily aggregates)
Rate Detects unusual call frequency spikes for a job Periodic sweep
Learned Band Builds a rolling baseline of normal cost per job, flags deviations beyond the learned_band_multiplier Periodic sweep

low1×–2× ceilingLogged, visible in Observatory dashboard

Per-Job Cost Bands

Every registered job has a cost band in lib/observatory/job-registry.ts. Bands are derived from the model tier with manual overrides for heavy-context jobs:

Tier DefaultPer-Call Ceiling (AUD)Daily Ceiling (AUD)
Opus$1.50$75
Sonnet$0.25$25

Heavy-context overrides raise the ceiling for specific jobs. For example, cockpit-brief gets $5.00 per call and $150 daily because it ingests the entire day’s operational context. brand-dna-generate-prose-portrait gets $3.00 per call because it reads 25+ tags, prior insights, reflection text, and business context.

High-volume Haiku classifiers (inbox routing, keyword scoring, ICP filtering) get elevated daily ceilings ($25 vs the default $10) because they fire many times per day by design.

Section 12

Implementation Tips

  1. Start with the registry pattern. Before writing a single prompt, set up the three-file structure: models.ts (registry), invoke.ts (entry point), and a cost-logging helper. Every LLM call you add later flows through this. Retrofitting a registry onto spaghetti SDK imports is miserable work.
  2. Enforce the boundary with a lint rule. SuperBad Lite uses a custom ESLint rule that blocks @anthropic-ai/sdk imports outside lib/ai/. This is not optional — without enforcement, someone will eventually bypass the registry “just this once” and the pattern erodes. Write the rule before the first feature ships.
  3. Name the job, not the model. Feature code says "brand-dna-generate-prose-portrait", never "claude-opus-4-6". This is the single design decision that makes the whole system flexible. When Anthropic releases a new model, you update one constant. When you realise a Haiku job needs better output, you change one word.
  4. Typed prompt builders are worth the overhead. Every prompt builder takes a typed input and returns a string. This means you catch missing context at compile time, not at runtime when the LLM produces garbage because it didn’t get the tags it needed.
  5. Cost logging must be fire-and-forget. Never let a logging failure block an LLM response. The user does not care that your analytics insert failed. They care that their Brand DNA portrait didn’t generate.
  6. Kill switches are not optional. Every autonomous LLM call — anything that fires without a human clicking a button — must be gated by a kill switch. The switch should default to false. You flip it on when you’re confident. When something goes wrong at 3am, you flip it off without deploying code.
  7. Track cost per actor, not just per call. The actorType + actorId fields on cost logs are what make per-subscriber margin analysis possible. Without them, you know how much you’re spending on LLMs total — but not whether any single subscriber is costing you more than they’re paying. For a SaaS product, that distinction is everything.
  8. Anomaly detection pays for itself. A runaway loop calling Opus 500 times because of a pagination bug will cost you real money. Per-call ceiling checks (sync, on every call) catch individual expensive calls. Daily sweeps catch accumulation. The learned-band detector catches drift that doesn’t violate hard thresholds but is still unusual.
  9. Brand voice drift checking is a feature, not overhead. If your platform sends emails on behalf of clients, those emails carry the client’s brand. A cheap Haiku call that scores the draft against the client’s voice profile is insurance. The threshold is configurable — start at 0.7 and tune from there.
  10. Separate the API key from env vars. SuperBad Lite stores the Anthropic API key encrypted in the database (via a setup wizard), with process.env as a local dev fallback. This means the production key never touches .env files, and rotating the key is a database update, not a redeploy.
  11. The prompt is the product. The code is plumbing. The registry is infrastructure. The thing that determines whether your Brand DNA portrait makes someone feel genuinely understood or reads like a horoscope is the prompt. Invest 80% of your effort there. Every voice constraint, every banned phrase, every structural rule in the prompt builders exists because the output was worse without it.
