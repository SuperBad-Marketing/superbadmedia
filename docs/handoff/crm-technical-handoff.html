Section 01

What the CRM Does

The CRM is the operational backbone of SuperBad Lite. It tracks every business relationship from first contact through to retained client — across three core entities: Companies, Contacts, and Deals.

Companies are the top-level entity. Every contact belongs to a company. Every deal belongs to a company and optionally links to a primary contact. This three-table structure supports everything from a solo founder with one decision-maker to a multi-stakeholder organisation with several contacts and concurrent deals.

The sales pipeline is an 8-stage Kanban board that visualises where every deal sits. Deals move forward through defined legal transitions, with validation rules enforced at terminal stages (Won and Lost). A separate trial shoot sub-state machine tracks the on-site photography session that is the primary conversion mechanism.

Everything that happens — every stage change, every email, every note, every payment — writes a row to the unified activity log. 334 distinct event kinds, across 40+ feature domains, all flowing into the same table.

One table to log them all. One table to find them.

Dedupe Logic

On creation, companies are deduplicated by normalised name (case-folded, whitespace-squeezed, punctuation stripped). If a domain is provided, it further narrows the match. Existing companies are never overwritten — only null fields get backfilled from incoming data.

Normalisation
function normaliseCompanyName(raw: string): string | null {
  return raw.trim().toLowerCase()
    .replace(/\s+/g, " ")
    .replace(/[.,'"!?]/g, "");
}

function normaliseDomain(raw: string): string | null {
  return raw.trim().toLowerCase()
    .replace(/^https?:\/\//, "")
    .replace(/^www\./, "")
    .replace(/\/.*$/, "");
}

Section 06

Deal Stage Transitions

Legal Transitions Map

Not every stage can reach every other stage. The LEGAL_TRANSITIONS adjacency map defines exactly which moves are allowed:

lead         →  contacted, conversation, trial_shoot, quoted, lost
contacted    →  lead, conversation, trial_shoot, quoted, lost
conversation →  lead, contacted, trial_shoot, quoted, negotiating, lost
trial_shoot  →  conversation, quoted, negotiating, lost
quoted       →  conversation, trial_shoot, negotiating, won, lost
negotiating  →  conversation, trial_shoot, quoted, won, lost
won          →  (terminal — no transitions out)
lost         →  lead (reopen only)
Key Rules

Won is forever. Once a deal hits won, it stays there. No backsies.

Lost can reopen. A lost deal can be moved back to lead to restart the pipeline. This is the only exit from a terminal stage.

Won requires won_outcome. You must specify retainer, saas, or project.

Lost requires loss_reason. And if the reason is other, free-text loss_notes are mandatory.

Transition Function

transitionDealStage(dealId, toStage, opts) is the single entry point for all non-terminal transitions. It runs inside a SQLite transaction that:

  1. Reads the current deal row
  2. Rejects identity transitions (already in that stage)
  3. Validates the move against LEGAL_TRANSITIONS
  4. Runs validateDeal() on the simulated new state
  5. Updates the deal row (stage, last_stage_change_at_ms, clears next_action_overridden_at_ms)
  6. Writes a stage_change activity log row with meta: { from_stage, to_stage, by }
  7. Returns the updated DealRow

Finalisation Functions

Terminal transitions use dedicated functions that set required fields before calling transitionDealStage():

Won
function finaliseDealAsWon(dealId, payload, opts) {
  // Inside one transaction:

Section 07

Trial Shoot State Machine

The trial shoot is the primary conversion mechanism: a free on-site photography session that demonstrates SuperBad’s value. While the deal sits in the trial_shoot pipeline stage, the company tracks a separate sub-state machine for the shoot’s lifecycle.

The Six States

none → booked → planned → in_progress → completed_awaiting_feedback → completed_feedback_provided
StatusMeaning
nonePre-booking placeholder. Every company starts here.
bookedTrial shoot booked (via Stripe payment or manual).
plannedShoot logistics confirmed. Date/location locked.
in_progressShoot day. Currently happening.
completed_awaiting_feedbackShoot done, deliverables in progress, feedback not yet received.
completed_feedback_providedClient has given feedback. Full lifecycle complete.

Forward-Only Transitions

The trial shoot state machine is strictly forward-only. Regression throws an error. This is enforced by comparing array indices:

TypeScript
function isForwardTransition(from: TrialShootStatus, to: TrialShootStatus): boolean {
  return indexOf(to) > indexOf(from);
}

function isTrialShootComplete(status: TrialShootStatus): boolean {
  return status === "completed_awaiting_feedback"
      || status === "completed_feedback_provided";
}

function legalForwardTargets(from: TrialShootStatus): TrialShootStatus[] {
  return SEQUENCE.slice(indexOf(from) + 1);
}

Booking Flow

markCompanyTrialShootBooked(dealId, opts) is the primary entry point, typically fired by the Intro Funnel Stripe webhook. In one transaction it:

  1. Moves the deal to trial_shoot stage (skipped if already there)
  2. Advances the company’s trial_shoot_status to booked (skipped if already at or past booked)
  3. Writes a trial_shoot_booked activity log row

Completion Timestamp

trial_shoot_completed_at_ms is stamped on the company the first time the status enters a completed_* state. Subsequent advances (e.g. completed_awaiting_feedback → completed_feedback_provided) do not overwrite it.

Deal vs Company

The deal stays in the trial_shoot pipeline stage for the entire sub-lifecycle. The granular state lives on the company’s trial_shoot_status column. This separation means one company can have trial shoot state independent of deal-level pipeline position.

How Events Are Written

Two patterns coexist:

  1. Inline in transactions — CRM functions (e.g. transitionDealStage, advanceTrialShootStatus) write activity rows inside the same SQLite transaction as the data mutation. Guarantees consistency.
  2. Via logActivity() helper — An async function that inserts a row using the default database connection. Used by server actions and background tasks where the event is independent of a transaction boundary.
logActivity Helper
async function logActivity(input: {
  companyId?: string;
  contactId?: string;
  dealId?: string;
  kind: ActivityLogKind;
  body: string;
  meta?: Record<string, unknown>;
  createdBy?: string;
  createdAtMs?: number;
}): Promise<ActivityLogRow>

Meta Shape Convention

The meta column is unstructured JSON, but conventions exist by kind:

  • stage_change: { from_stage, to_stage, by, source? }
  • note (snooze): { kind: "snooze", until_ms, by }
  • note (trial shoot): { kind: "trial_shoot_status_change", from, to, by }
  • note (plan update): { kind: "trial_shoot_plan_updated", by, length }

The note kind doubles as a catch-all. Distinguish sub-types via meta.kind.

Section 09

Stale Detection

A deal is “stale” when it has sat in a stage too long without advancing. Stale detection runs on every pipeline page load and drives visual indicators on the Kanban board.

Per-Stage Thresholds

Each non-terminal stage has a configurable threshold in days, stored in the settings table:

Setting KeyStage
pipeline.stale_thresholds.lead_dayslead
pipeline.stale_thresholds.contacted_dayscontacted
pipeline.stale_thresholds.conversation_daysconversation
pipeline.stale_thresholds.trial_shoot_daystrial_shoot
pipeline.stale_thresholds.quoted_daysquoted
pipeline.stale_thresholds.negotiating_daysnegotiating

Staleness Logic

isDealStale() is a pure function — no database access, no side effects. It takes the deal’s stage, timestamps, and the threshold config:

TypeScript
function isDealStale(deal, thresholds, nowMs): boolean {
  // 1. Won / Lost are terminal → never stale
  // 2. Null last_stage_change_at_ms → not stale (defensive)
  // 3. Snoozed until future date → suppressed (not stale)
  // 4. Compare: (now - last_stage_change) > (threshold_days * 86400000)
  const key = THRESHOLD_KEY_FOR_STAGE[deal.stage];
  if (!key) return false;
  if (deal.snoozed_until_ms != null && deal.snoozed_until_ms > nowMs)
    return false;
  return nowMs - deal.last_stage_change_at_ms > thresholds[key] * DAY_MS;
}

Snooze Suppression

A deal can be snoozed until a future date. While snoozed, it is excluded from stale detection. Once the snooze expires, normal staleness computation resumes.

snoozeDeal(dealId, untilMs, opts) sets the snoozed_until_ms column and writes a note activity row with meta: { kind: "snooze" }. The snooze date must be strictly in the future.

The default snooze duration is configurable via pipeline.snooze_default_days in the settings table.

No Background Job

Stale detection is computed on read, not written by a cron job. Every time the pipeline page loads, every deal is evaluated against the current time and current thresholds. This means threshold changes take effect immediately with zero migration.

Auth Pattern

Every action uses the same guard:

TypeScript
async function adminActorTag(): Promise<string | null> {
  const session = await auth();
  if (!session?.user || session.user.role !== "admin") return null;
  return `user:${session.user.id ?? "admin"}`;
}

This tag flows into activity_log.created_by and meta.by on every event.

Section 12

Implementation Tips

  1. Start with the three core tables. Companies, Contacts, Deals — and the relationships between them. Everything else hangs off these. Get the foreign key cascade rules right first.
  2. Normalise on write, match on normalised columns. Store both the raw input (email) and the normalised version (email_normalised). Index the normalised columns. Never normalise on read — it kills index performance.
  3. Dedupe is non-destructive. When a duplicate is found, only null fields are backfilled. Never overwrite existing data. This prevents accidental data loss from bad imports.
  4. Legal transitions are a map, not a matrix. A simple Record<DealStage, DealStage[]> is easier to read, extend, and test than a 2D boolean matrix. Loop through the adjacency list to render valid move targets in the UI.
  5. Terminal stages need dedicated finalisation functions. Don’t let the generic transition function handle Won/Lost. The required metadata fields (won_outcome, loss_reason) must be set in the same transaction as the stage change, or you’ll end up with Won deals that don’t say what was won.
  6. Staleness is computed on read, not written by cron. This means threshold changes take effect immediately. It also means the isDealStale() function must be pure — no database access, no side effects, just math.
  7. Snooze suppresses stale, it doesn’t reset the clock. When a snooze expires, staleness is recalculated from the original last_stage_change_at_ms. The deal might be immediately stale when it unsnozes. This is correct.
  8. Write activity log rows inside the same transaction. If the stage change succeeds but the activity log insert fails (or vice versa), your audit trail is wrong. SQLite transactions make this free.
  9. The note kind is a catch-all. Use meta.kind to sub-type it ("snooze", "trial_shoot_status_change", "trial_shoot_plan_updated"). Don’t create a new top-level kind for every variation.
  10. Trial shoot state lives on the company, not the deal. A company’s trial shoot is a single event even if the pipeline deal changes. The deal stays in trial_shoot stage while the company’s trial_shoot_status tracks the granular lifecycle.
  11. Value is always in cents. Never store dollars as a float. Display formatting happens at the boundary (value_cents / 100). Use Intl.NumberFormat for currency display.
  12. Every action returns a discriminated union. { ok: true } or { ok: false; error: string }. The client can toast the error directly. Never throw from a server action — the error serialisation is unreliable.
Final Note

The CRM is boring on purpose. Three tables, eight stages, one activity log. The complexity lives in the business rules — which transitions are legal, when a deal goes stale, what metadata a Won needs. Get the rules right and the code stays simple.
