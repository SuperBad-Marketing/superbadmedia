Section 01

What the Auth System Does

SuperBad Lite has three entirely separate authentication surfaces, each serving a different audience and using a different mechanism. They share no session state.

SurfaceWhoMechanismSession Storage
Admin Andy (sole admin) Email + password via NextAuth v5 Credentials provider JWT (httpOnly cookie managed by Auth.js)
Subscriber SaaS subscribers (prospects promoted to clients) Magic link emailed on first Stripe payment or on demand JWT (same NextAuth session — user gets a real user row)
Portal Prospects and clients (intro funnel, client management) Magic link → base64url-encoded httpOnly cookie Lightweight custom cookie (sbl_portal_session)

The admin surface is gated by two sequential middleware checks — the Brand DNA Gate and the Critical Flight Gate — that force onboarding completion before the admin dashboard is accessible. The portal surface is entirely outside middleware; it validates its own session cookie in Server Components.

There is also a Bench surface for hiring candidates, which uses the same magic-link-to-cookie pattern as the portal but with its own cookie (sbl_bench_session) and a separate token table.

Three auth surfaces, zero shared sessions. That’s not an accident.

Section 02

Architecture

The Split Config Pattern

NextAuth v5 (Auth.js) requires special care in Next.js because middleware runs on the Edge Runtime, which cannot load native Node.js modules. SuperBad Lite solves this with a “split config” pattern — two files that share the same base configuration but diverge on what they import:

FileRuntimeWhat It Does
lib/auth/auth.config.ts Edge-safe Session strategy (jwt), page routes, JWT + session callbacks. No DB imports. Imported by middleware.
lib/auth/auth.ts Node.js only Extends authConfig with the Credentials provider (DB lookup), JWT override (Brand DNA + Critical Flight checks), sign-in events. Never imported from middleware. 
proxy.ts (middleware)
  ↓ imports
  auth.config.ts ← Edge-safe, no DB, no native modules
    • session strategy: "jwt"
    • pages: signIn → "/lite/login"
    • jwt callback: sets id, role, brand_dna_complete, critical_flight_complete
    • session callback: shapes session.user for Server Components

lib/auth/auth.ts
  ↓ imports
  auth.config.ts + extends with:
    • Credentials provider (DB lookup via better-sqlite3)
    • jwt override: re-queries Brand DNA + Critical Flight status on signIn/update
    • signIn event: logs admin activity, enqueues morning digest

lib/auth/session.ts
  • Re-exports auth(), signIn(), signOut() from auth.ts
  • TypeScript module augmentation for session.user

Provider Configuration

A single Credentials provider handles both admin and subscriber login. The authorize() function branches on the presence of a subscriberLoginToken field:

  • If a token is present: subscriber magic-link flow — redeems the token, promotes prospect → client, returns the user.
  • If email + password are present: admin login flow — looks up the user, verifies the password hash, confirms role is admin.

No OAuth providers are configured. No email/magic-link providers are configured at the NextAuth level — magic links are handled through custom route handlers that call signIn() server-side.

Section 03

Authentication Flows

3.1 — Admin Login (Email + Password)

1. User visits /lite/login
2. Client-side form calls signIn("credentials", { email, password })
   (uses next-auth/react — NOT a server action)
3. Auth.js POST to /api/auth/callback/credentials
4. authorize() runs:
   a. DB lookup by email
   b. Verify role === "admin"
   c. Verify password via scrypt timing-safe comparison
   d. Return user object { id, email, name, role }
5. JWT callback fires:
   a. Edge-safe base: sets token.id, token.role, defaults brand_dna_complete = false
   b. Node-side override: queries DB for Brand DNA status + Critical Flight status
6. Session callback fires: shapes session.user with all custom claims
7. signIn event fires: logs "admin_session_started", enqueues task digest
8. Client-side redirect to /lite/admin/pipeline (or callbackUrl)
Why Client-Side signIn

NextAuth v5 beta has a known issue where server-action signIn() silently breaks credential passing. The login page uses next-auth/react client-side signIn() with redirect: false and handles the redirect manually. This is intentional.

3.2 — Subscriber Magic Link

1. Stripe invoice.payment_succeeded webhook fires (first successful cycle)
   OR subscriber clicks "send me my login" on /get-started/welcome
2. issueSubscriberMagicLink({ userId }):
   a. Generate 32-byte random token (base64url)
   b. SHA-256 hash the token
   c. Store hash + metadata in subscriber_magic_link_tokens
   d. Build URL: /api/auth/magic-link?token=<raw>
3. Token emailed to subscriber (raw token only in email body)
4. Subscriber clicks link → GET /api/auth/magic-link?token=...
5. Route handler calls signIn("credentials", { subscriberLoginToken })
6. authorize() → redeemSubscriberMagicLink():
   a. Hash the raw token, look up the row
   b. Reject if consumed / expired / user missing
   c. Mark token consumed (double-consume guard via WHERE consumed_at_ms IS NULL)
   d. If user.role = "prospect" → promote to "client", set first_signed_in_at_ms
   e. Mark email as verified (idempotent)
   f. Log activity
   g. Return user object
7. Auth.js issues JWT session cookie
8. Redirect to /lite/onboarding (or custom redirect param)

3.3 — Portal Magic Link (Prospects & Clients)

1. System issues a portal link (journey-beat email, admin action, recovery form):
   issueMagicLink({ contactId, clientId?, submissionId? })
   a. Generate 32-byte random token (base64url)
   b. SHA-256 hash → store in portal_magic_links.ott_hash
   c. Build URL: /lite/portal/r/<raw-token>
2. Recipient clicks link → GET /lite/portal/r/[token]
3. redeemMagicLink(rawToken):
   a. Hash token, look up row
   b. Reject if consumed or expired
   c. Mark consumed, log activity
   d. Return { contactId, clientId, submissionId }
4. Encode session payload as base64url JSON
5. Set sbl_portal_session cookie (httpOnly, Secure, SameSite=Lax, 90-day TTL)
6. Redirect to /lite/portal/welcome (first visit) or /lite/portal/home

Portal sessions do not go through NextAuth at all. Completely separate cookie, completely separate validation.

3.4 — Bench Magic Link (Hiring Candidates)

Identical pattern to portal magic links but uses the bench_magic_links table and a separate sbl_bench_session cookie. Candidates get a link, click it, the token is redeemed, and a lightweight cookie session is issued. Archived candidates are rejected at redemption.

Section 04

Middleware Gates

The middleware (proxy.ts at project root) runs on every request matching /((?!_next/static|_next/image|favicon.ico).*). It implements two sequential gates that only apply to authenticated admin routes under /lite/.

Public Route Bypass

These paths skip both gates entirely — no auth check at all:

PatternReason
/api/auth/*NextAuth endpoints (signin, signout, session, CSRF)
/lite/portal/*Portal has its own cookie auth
/lite/onboardingBrand DNA gate target — must not loop
/lite/loginAdmin sign-in page
/lite/designDesign gallery (dev tool)
/lite/legal/*Legal pages are publicly accessible
/lite/quotes/*Client-facing quotes (token-gated internally)
/lite/invoices/*Client-facing invoices (token-gated internally)
/lite/brand-dna/*Brand DNA assessment (auth resolved inside Server Components)
/api/*API routes handle their own auth
/_next/*Next.js internals
/favicon.icoStatic asset

Auth Check

If the request is not public and starts with /lite, middleware checks req.auth. If absent, redirects to /lite/login?callbackUrl=<current-path>.

Gate 1 — Brand DNA Gate

Gate 1: Brand DNA

Condition: session.user.brand_dna_complete === false
Redirect:  /lite/onboarding
Bypass:    env BRAND_DNA_GATE_BYPASS=true

Purpose: Forces Andy to complete his own Brand DNA assessment
before he can access the admin dashboard. Self-terminates when
the SuperBad-self profile is completed and a session refresh
flips brand_dna_complete to true.

The brand_dna_complete flag is cached in the JWT. It starts as
false at sign-in. The Node-side jwt callback re-queries the DB
via isBrandDnaCompleteForUser() on signIn, signUp, or
session.update() triggers.

Gate 2 — Critical Flight Gate

Gate 2: Critical Flight

Condition: session.user.critical_flight_complete === false
Redirect:  /lite/first-run
Bypass:    Routes starting with /lite/first-run or /lite/setup/

Purpose: Ensures every critical setup wizard has been completed
before the admin dashboard is accessible. The /lite/first-run
page reads the wizard sequencer and redirects to the next
incomplete wizard.

Critical wizards (from settings): stripe-admin, resend, graph-api-admin
All three must have at least one wizard_completions row for the user.

The critical_flight_complete flag is cached in the JWT and
refreshed on signIn / session.update() via
hasCompletedCriticalFlight(), which delegates to
getCriticalFlightStatus().

Gate Execution Order

Request to /lite/admin/*
  ↓
Is public route? → Yes → NextResponse.next()
  ↓ No
Starts with /lite? → No → NextResponse.next()
  ↓ Yes
Has auth? → No → Redirect to /lite/login
  ↓ Yes
Gate 1: brand_dna_complete? → No → Redirect to /lite/onboarding
  ↓ Yes
Gate 2: critical_flight_complete? → No → Redirect to /lite/first-run
  ↓ Yes
NextResponse.next() ← request proceeds

The can() Function

Route-level access control is enforced by can(role, action, resource) in lib/auth/permissions.ts. Default-deny: any rule miss returns false.

function can(role: Role, action: Action, resource: string): boolean

// Example usage in a Server Component or API route:
if (!can(session.user.role, "GET", "/lite/finance/expenses")) {
  return new Response("Forbidden", { status: 403 });
}

Section 07

Magic Link System

Three separate magic-link implementations serve different audiences, but they all follow the same cryptographic pattern:

Token Lifecycle

1. Generate
   raw = randomBytes(32).toString("base64url")   ← 256-bit entropy
   hash = SHA-256(raw).hex()

2. Store
   INSERT token_hash, user_id/contact_id, expires_at_ms, consumed_at_ms = NULL
   Only the hash is persisted. The raw token is returned to the caller
   and embedded in the email body. It never touches the database.

3. Deliver
   Email body contains the full URL with the raw token:
   Subscriber: /api/auth/magic-link?token=<raw>
   Portal:     /lite/portal/r/<raw>
   Bench:      /bench/r/<raw>

4. Redeem
   hash = SHA-256(raw).hex()
   SELECT WHERE token_hash = hash
   Reject if: not found, consumed_at_ms IS NOT NULL, expires_at_ms < now
   UPDATE SET consumed_at_ms = now
   (Double-consume guard: subscriber tokens use a WHERE clause
    with consumed_at_ms IS NULL + expires_at_ms >= now in the UPDATE)

5. Expire
   Tokens past their TTL are implicitly dead — the redeem check
   rejects them. No cleanup cron needed.

TTL Configuration

subscriber.magic_link_ttl_hours24 hoursSubscriber login tokens
portal.magic_link_ttl_hours168 hours (7 days)Portal + Brand DNA invite tokens

Why Store Only Hashes

If the database is compromised, an attacker who has token hashes cannot use them to log in. The raw token only ever exists in the email body and the URL at click time. This is the same pattern used by password reset tokens in any serious auth system.

Portal Authentication

The portal (for prospects and clients) runs a completely separate authentication system from the admin NextAuth flow. No user table row is required — portal sessions are tied to contacts rows.

Session Recovery

When a portal session cookie is missing or expired, the user is redirected to /lite/portal/recover. The recovery form takes an email, looks up the contact (first in intro_funnel_submissions, then in contacts), and issues a fresh magic link. Both success and “not found” return silently to prevent email enumeration.

PATCHES_OWED: Cookie Signing

The portal session cookie is currently base64-encoded JSON without cryptographic signing. A future session adds signing (e.g. iron-session or JWT). Tracked as a8_portal_cookie_unsigned. Do not store sensitive data beyond the contact/client id in this cookie.

Section 09

Session Management

JWT Strategy (Admin + Subscriber)

SuperBad Lite uses JWT sessions (not database sessions). The session strategy is declared in auth.config.ts:

Configuration
session: { strategy: "jwt" }

This means session data lives entirely in a signed, httpOnly cookie. No session table in the database. The tradeoff: you cannot revoke individual sessions server-side without changing the JWT secret (which invalidates all sessions).

JWT Token Shape

TypeScript — Custom JWT Claims
// Set by the Edge-safe jwt callback (auth.config.ts):
token.id: string              // User row id
token.role: string            // "admin" | "client" | "prospect"
token.brand_dna_complete: boolean  // Starts false; refreshed on signIn/update
token.critical_flight_complete: boolean  // Starts false; refreshed on signIn/update

// Plus standard Auth.js fields: sub, iat, exp, jti

Session Object Shape

TypeScript — session.user (Server Components)
session.user.id: string
session.user.role: string
session.user.brand_dna_complete: boolean
session.user.critical_flight_complete: boolean
session.user.name?: string
session.user.email?: string
session.user.image?: string

Token Refresh Triggers

The Node-side jwt callback (in auth.ts) overrides the Edge-safe base and re-queries the database for brand_dna_complete and critical_flight_complete on three triggers:

  • signIn — initial login
  • signUp — first-time sign-up
  • update — explicit session.update() call (e.g. after Brand DNA completion or wizard finish)

On all other token renewals (page navigation, cookie refresh), the cached values carry forward unchanged. This means the gates only lift after a deliberate session update.

Module Augmentation

lib/auth/session.ts augments the NextAuth types so session.user is fully typed across the codebase:

TypeScript — Module Augmentation
declare module "next-auth" {
  interface Session {
    user: {
      id: string;
      role: string;
      brand_dna_complete: boolean;
      critical_flight_complete: boolean;
    } & DefaultSession["user"];
  }
}
Usage Pattern

Import auth from @/lib/auth/session (not from @/lib/auth/auth directly). The session module re-exports auth, signIn, and signOut and ensures the type augmentation is always loaded.

Section 10

Security Considerations

Password Hashing

Admin passwords are hashed using scrypt (Node.js built-in crypto.scryptSync) with the following parameters:

ParameterValueWhat It Does
Key length64 bytesOutput hash size
Cost (N)16384CPU/memory cost factor (214)
Block size (r)8Memory usage multiplier
Parallelization (p)1Parallelism factor

Storage format: salt:derivedKey (both hex-encoded). Salt is 16 random bytes per password. Comparison uses timingSafeEqual to prevent timing attacks.

Token Security

  • 256-bit entropy: all magic-link tokens are 32 random bytes (base64url-encoded), giving 2256 possible values.
  • Hash-only storage: only the SHA-256 hash is stored in the database. A database breach does not leak usable tokens.
  • Single use: tokens are marked consumed on first redemption. The subscriber flow uses an atomic UPDATE ... WHERE consumed_at_ms IS NULL to prevent race conditions.
  • TTL enforcement: every redeem checks expires_at_ms < now before accepting.

CSRF Protection

NextAuth v5 handles CSRF protection automatically via its /api/auth/csrf endpoint. The Credentials provider login form uses the client-side signIn() from next-auth/react, which includes the CSRF token in the request.

Cookie Security

CookiehttpOnlySecureSameSiteSigning
NextAuth session (JWT)YesYes (prod)LaxYes (Auth.js signs JWTs)
sbl_portal_sessionYesYes (prod)LaxNo (base64 only — PATCHES_OWED)
sbl_bench_sessionYesYes (prod)LaxNo (base64 only)

Open Redirect Prevention

The subscriber magic-link route handler validates the redirect parameter starts with /lite/ before using it. Arbitrary URLs are rejected and the flow falls back to /lite/onboarding. The portal redeem endpoint validates that callbackUrl starts with /lite/ as well.

Email Enumeration Prevention

The portal recovery form (requestPortalLink) always returns void regardless of whether the email was found. Both “success” and “not found” look identical to the caller, preventing attackers from confirming which emails have accounts.

Admin-Only Password Login

The authorize() function explicitly checks that the user’s role is admin before allowing email + password login. Non-admin users (clients, prospects) cannot authenticate via the password form — they must use magic links. This prevents credential-stuffing attacks on the broader user base.

Section 11

Kill Switches

Three kill switches directly affect the auth system. They are defined in lib/kill-switches.ts and evaluated at runtime.

SwitchDefaultWhat It Gates
brand_dna_assessment_enabled true When false, isBrandDnaCompleteForUser() short-circuits to false — the Brand DNA gate in middleware will always redirect to onboarding. In practice, this switch controls the entire Brand DNA feature, and the gate bypasses via BRAND_DNA_GATE_BYPASS=true env var.
setup_wizards_enabled true When false, hasCompletedCriticalFlight() short-circuits to true — gate 2 is effectively disabled. All wizard sequencing, nudges, and completion checks are bypassed.
llm_calls_enabled true Indirectly affects auth: when false, Brand DNA generation returns stub text, which means the profile may not reach status = "complete" through the normal flow. Does not gate auth itself.

Runtime Override

Kill switches can be overridden at process boot via the KILL_SWITCHES_ON environment variable (comma-separated list of switch keys). This is intended for development and Playwright tests, not production. Example:

Environment
KILL_SWITCHES_ON=brand_dna_assessment_enabled,setup_wizards_enabled

Middleware Bypass

The Brand DNA gate has a dedicated bypass separate from kill switches:

Environment
BRAND_DNA_GATE_BYPASS=true  // Skips gate 1 in middleware

This does not disable the Brand DNA feature — it only stops the middleware redirect. The assessment can still be taken; it just isn’t forced.

Section 12

Implementation Tips

  1. Respect the Edge/Node split. The most common NextAuth v5 mistake is importing Node.js modules (database drivers, crypto) into a file that runs in Edge middleware. Keep your middleware config pure — no DB calls, no native modules. Move all database-dependent logic into the Node.js-only auth file.
  2. Use client-side signIn for Credentials. NextAuth v5 beta has a known issue where server-action signIn() silently drops credential fields. Always use next-auth/react with redirect: false and handle the redirect manually.
  3. Magic links are cheap and reliable. If you are building a SaaS where users are invited (not self-registering with passwords), magic links are the right default. Users do not need to remember a password, and you do not need a password-reset flow. Store only the hash, enforce TTL, mark consumed on first use.
  4. Keep portal auth separate from admin auth. If you have different audiences (admins vs customers), give them completely separate session mechanisms. Trying to make one auth system serve both will create role-escalation risks and make middleware impossibly complex.
  5. Gate onboarding at the middleware level. If there are setup steps the admin must complete before the platform is useful, enforce them in middleware with JWT-cached flags. This is vastly more robust than checking completion status on individual pages.
  6. Default-deny in your RBAC. Your can() function should return false for any rule it does not explicitly recognise. Forgetting to add a rule should lock people out, not let them in.
  7. Use timing-safe comparison everywhere. Not just passwords. If you ever compare two secrets (tokens, hashes, API keys), use timingSafeEqual. Timing attacks are real and trivially exploitable.
  8. Prevent email enumeration on recovery forms. Always return the same response whether the email exists or not. The recovery form says “if that email has an account, we sent a link” — never “email not found.”
  9. Validate redirect URLs. Any callbackUrl or redirect parameter that influences where the user ends up after auth must be validated against a known prefix (e.g. /lite/). Otherwise you have an open redirect vulnerability that phishing campaigns love.
  10. Kill switches let you ship and gate independently. Deploy auth-gated features with the kill switch off, verify in production, then flip the switch. Rolling back is one env var change, not a redeploy.
