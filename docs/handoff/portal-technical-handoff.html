Section 01

What the Client Portal Does

The Client Portal is the customer-facing half of SuperBad Lite. Every client — from a prospect who just booked a trial shoot to a retainer client paying monthly — gets their own portal at /lite/portal/[token]. It is a passwordless, token-authenticated environment that feels like the client’s own private room, not a shared platform.

The portal is chat-first. The landing page is always the AI Bartender — a conversational AI concierge that greets the client by name, knows their deal stage, invoice status, and Brand DNA profile, and can answer questions or escalate to the human operator. Navigation to other sections (gallery, deliverables, invoices, plan) happens through a floating menu bubble.

Client-facing surfaces never show “SuperBad Lite.” Clients see “SuperBad” everywhere. The “Lite” label is internal only.

Their room. Their name on the door. The bartender knows what they’re drinking.

Who uses it

  • Pre-retainer prospects — people who booked a trial shoot. They get a subset of the portal: chat, gallery, Brand DNA, and their 6-week marketing plan.
  • Retainer clients — paying monthly subscribers. Full portal access: invoices, messaging, package details, data export, plus everything above.
  • SaaS subscribers — users of standalone products. They enter through the subscription/welcome path and follow a separate onboarding flow with revenue segmentation.

Shell Architecture

The [token] layout wraps all portal sub-pages in a PortalShell component. The shell provides:

  • Top bar — “SuperBad” brand mark on the left, “[name]’s room” on the right.
  • Ambient background — layered radial gradients (orange, red, pink) + SVG noise overlay. These are fixed-position, pointer-events-none, and create a warm atmosphere without affecting content.
  • Menu bubble — floating button that opens a full-page overlay menu. Sections are filtered by portal mode (pre-retainer sees fewer items).
  • Chat bubble — persistent bottom-right floating button on all non-chat pages. Navigates back to the chat home.
  • Referral prompt — contextual prompt shown at milestone moments (cooldown-gated).

Section 03

Portal Modes

Every portal visit computes a mode from the contact’s deal state. The mode determines which sections are visible, which are locked, and what the AI bartender knows about the relationship.

TypeScript — lib/portal/mode.ts
type PortalMode = "pre_retainer" | "retainer" | "archived";

interface PortalModeResult {
  mode: PortalMode;
  brandDnaComplete: boolean;
  retainerKickoffSaid: boolean;
}

Mode derivation logic

ModeConditionSections Visible
retainer Company has a deal with stage = "won" and subscription_state in ["active_current", "past_due", "paused"] All 9 sections
pre_retainer Everything else — trial-shoot prospect, in-progress deal, non-converter Chat, Deliverables, Brand DNA, Gallery, Your Plan
archived 60-day post-shoot non-converter (future — currently falls back to pre_retainer) Read-only archive view

The getPortalMode() function runs three queries: contact lookup, deal status check, and Brand DNA profile check. The Brand DNA completion flag is used by the retainer mode’s hard lock (see Section 6).

Section definitions

Sections are declared in a static PORTAL_SECTIONS array. Each section has a preRetainer: boolean flag that controls visibility in pre-retainer mode. The menu bubble filters sections based on this flag.

When a pre-retainer user navigates to a locked section (invoices, messages, package, data export), the server component renders a SectionLocked component instead of the actual content. No data is fetched, no content is leaked.

Section 04

Authentication

The Magic Link Flow

1. Issue: Generate 32-byte random token → SHA-256 hash
   Store hash in portal_magic_links table
   Send raw token via email: /lite/portal/r/{rawToken}

2. Redeem: Client clicks link → GET /lite/portal/r/[token]
   Hash the incoming token → look up in DB
   Reject if: consumed, expired, or not found
   Mark row as consumed (set consumed_at_ms)

3. Session: Encode { contactId, clientId, submissionId } as base64url
   Set sbl_portal_session httpOnly cookie (90-day TTL)
   Redirect to /welcome (first visit) or /home (returning)

4. Guard: Every portal page calls requirePortalSession()
   Decode cookie → return session or redirect to /recover

Token generation

The issueMagicLink() function at lib/portal/issue-magic-link.ts handles token creation:

  • Generates a cryptographically random 32-byte token using crypto.randomBytes(), encoded as base64url.
  • Stores only the SHA-256 hash (ott_hash) in the database. The raw token exists only in the email and the URL.
  • Default TTL is 168 hours (7 days), configurable via settings.get('portal.magic_link_ttl_hours').
  • Logs the issuance to the activity log with context (submission_id, client_id, purpose).

Token redemption

The redeemMagicLink() function at lib/portal/redeem-magic-link.ts validates and consumes tokens:

  1. Hash the incoming raw token with SHA-256.
  2. Look up the hash in portal_magic_links.
  3. Reject if not found, already consumed (consumed_at_ms not null), or expired.
  4. Set consumed_at_ms = Date.now() — the token is now single-use.
  5. Return the session payload: contactId, clientId, submissionId.

Session cookie

TypeScript — lib/portal/guard.ts
type PortalSession = {
  contactId: string;         // always present
  clientId: string | null;  // non-null for Client Management portals
  submissionId: string | null; // scopes to an intro-funnel submission
};

const PORTAL_SESSION_COOKIE = "sbl_portal_session";
// base64url(JSON.stringify(session))
// httpOnly, Secure (prod), SameSite=Lax, path=/
// Max-age: settings.get('portal.session_cookie_ttl_days') × 86400 (default 90 days)
Security Note

The session cookie is base64-encoded but not signed or encrypted. This is a known limitation with a patch owed (a8_portal_cookie_unsigned). In production, this should be upgraded to use iron-session or JWT signing. Do not store sensitive data in the cookie beyond the contact/client ID.

Recovery flow

When a session cookie is missing or malformed, users are redirected to /lite/portal/recover. This page has one field: email address. On submit:

  1. Look up the email in intro_funnel_submissions and contacts.
  2. If found, issue a fresh magic link via email.
  3. Always show “Check your inbox” — same response for match or no-match to prevent email enumeration.

The require pattern

Two guard functions are used throughout the portal:

requirePortalSession()lib/portal/require-session.tsRead cookie, redirect to /recover if absent
requireIntroSession(token)lib/portal/require-intro-session.tsSame, but passes a returnTo param for intro funnel
Section 05

AI Bartender

The AI Bartender is the heart of the portal. It is a conversational AI that greets clients, answers questions about their account, and escalates anything it cannot handle to the human operator. The chat is persistent — every message (both client and assistant) is stored in the database and survives across sessions.

System prompt

Bartender System Prompt

“You are the SuperBad portal bartender — the AI concierge for a creative marketing agency run by Andy Robinson in Melbourne. Your register is warm, observational, dry-humoured, never pitchy. You know the client’s name and use it naturally. Short responses preferred — bartender efficiency, not chatbot verbosity.”

Hard rules baked into the system prompt:

  • Never pitch services. Never use “synergy”, “leverage”, or “solutions”.
  • If asked whether you’re human: “No — but Andy is. Want me to get him?”
  • Never reveal other clients’ data or internal pipeline state.
  • Never hallucinate data not provided in context.
  • Keep responses to 1–3 sentences unless the client asks for detail.
  • No exclamation marks. No slogans. No emoji unless the client uses them first.

Context assembly

Before every response, the system assembles a context block from the database. This gives the LLM grounding in real data:

Context block structure
ChatContext {
  contactName: string;         // "Sarah Chen"
  companyName: string;         // "Good Earth Café"
  contactRole: string | null;  // "owner"
  brandDnaStatus: string | null; // "complete", "in_progress", null
  brandDnaProse: string | null;  // full prose portrait (fed to LLM)
  dealStage: string | null;    // "won", "trial_shoot", "quoted"
  wonOutcome: string | null;   // "retainer", "project"
  valueCents: number | null;   // deal value
  subscriptionState: string | null;
  billingCadence: string | null;
  pendingInvoiceCount: number;
  overdueInvoiceCount: number;
  isRetainer: boolean;
}

Two chat endpoints

Opening line — generated on every portal home page load. Uses a lighter prompt that produces one contextual greeting sentence. Has a special kickoffVariant for the first login after a deal closes (retainer kickoff). The system deduplicates: if the most recent message is already from the assistant, it returns that instead of generating a new one.

Chat response — the main conversation handler. Receives the client message, fetches the last 20 messages of conversation history, and feeds the full context (including the Brand DNA prose portrait) to the LLM. If the client’s Brand DNA is complete, the bartender literally has a psychological profile of the person it’s talking to.

Rate limiting

Daily chat limits are configurable via the settings table and differ by relationship type:

Setting KeyPurpose
portal.chat_calls_per_day_retainerDaily limit for retainer clients
portal.chat_calls_per_day_pre_retainerDaily limit for prospects

When the limit is hit, the API returns a 429 with a message directing the client to email the operator directly.

Escalation

When the bartender cannot handle a request (reschedule, cancel, edit profile, anything out of scope), it signals escalation by prefixing its response with [ESCALATE]. The system then:

  1. Strips the [ESCALATE] tag from the client-facing reply.
  2. Generates a separate internal summary using a Haiku prompt (concise, factual, internal voice).
  3. Creates a new thread in the unified inbox with channel "portal_chat".
  4. Inserts the summary as an inbound message on the thread.
  5. Logs the escalation to the activity log.

The client sees a clean response. Andy sees the escalation in his inbox with full context.

LLM jobs

Job NamePurposeMax Tokens
client-mgmt-bartender-opening-lineOpening greeting150
client-mgmt-chat-responseConversation reply500
client-mgmt-escalation-summaryInternal summary for Andy300

All calls route through the model registry via invokeLlmText(). Feature code never references a model ID.

Section 06

Brand DNA Gate

When a retainer client visits the portal and their Brand DNA assessment is not complete, the portal does not show the chat home. Instead, it renders the BrandDnaGate component — a full-page lock screen with a single CTA: “Complete your Brand DNA.”

Gate logic

Portal home loads
  └ if mode === "retainer" AND NOT brandDnaComplete:
      → render BrandDnaGate
      → log "retainer_mode_brand_dna_gate_entered"
  └ else:
      → continue to chat home / bundle hub

What the gate shows

  • A lock icon in a circular badge.
  • Eyebrow text: “one thing first.”
  • Heading: “Brand DNA.”
  • Personal message: “{firstName}, before we unlock the rest of your room — we need to understand your brand. takes about ten minutes.”
  • CTA button linking to /lite/portal/brand-dna.
  • Below: a grid of blurred section cards (Chat, Invoices, Deliverables, Package, Messages, Data Export) at reduced opacity with a slight CSS blur — showing the client what they’ll unlock.

Why this exists

Brand DNA is the data that powers everything downstream — the bartender’s personality awareness, the marketing plan’s strategic foundation, and the operator’s understanding of the client. Without it, the portal is running blind. The gate ensures retainer clients complete the assessment before they can use any other feature.

Pre-retainer prospects are not gated. They can explore the portal freely. The gate only applies to retainer clients because their portal experience is deeper and depends more heavily on Brand DNA data.

Section 07

Deliverables & Gallery

Deliverables (task-based)

The deliverables page surfaces tasks from the platform’s task management system. There is no separate deliverables data model — everything comes from the tasks table filtered by kind IN ('client_deliverable', 'client_task') and the client’s company.

Portal task shape
interface PortalTask {
  id: string;
  title: string;
  body: string;
  kind: "client_deliverable" | "client_task";
  status: "todo" | "in_progress" | "awaiting_approval" | "delivered" | "done";
  priority: "urgent" | "high" | "medium" | "low";
  due_at: string | null;
  checklist: Array<{ id: string; text: string; checked: boolean }> | null;
  approval_requested_at: string | null;
  approved_at: string | null;
  rejected_at: string | null;
  rejection_feedback: string | null;
}

Client actions on deliverables:

  • Approve — single click, marks the task as approved.
  • Reject — requires feedback text explaining the rejection.

There is also a separate /lite/portal/approve/[token] route for one-click approvals via email links, using a separate token-based auth that validates the token before executing the approval.

Gallery (Cloudinary-based)

The gallery serves photos and video from shoots. Media is stored in Cloudinary, organised by folder per deal.

Gallery page loads
  └ Read portal session
  └ Look up contact → company → deal with cloudinary_gallery_folder
  └ Call listFolder(folder) → Cloudinary Admin API
  └ Transform each resource into GalleryItem
  └ Generate ZIP archive URL via generateArchiveUrl(folder)
  └ Render gallery grid + “Download All” button

Each gallery item provides:

  • Thumbnail URL — 600px-wide Cloudinary transform with auto quality/format.
  • Full URL — original resolution via secure_url.
  • Download URL — same as full URL with ?fl_attachment to force browser download.
  • Archive URL — Cloudinary ZIP generation for the entire folder (graceful degradation if ZIP fails).

Bundle hub

On first visit after deliverables are ready, the portal shows a BundleHub instead of the normal chat home. This is a two-tile card layout: “Your photos & video” (gallery) and “Your plan” (6-week plan). The hub is one-shot — once the client clicks either tile, bundled_hub_seen_at_ms is set on the contact and the hub never re-shows.

Section 08

6-Week Plan

Every trial-shoot prospect receives a bespoke 6-week marketing plan, generated by the LLM pipeline and reviewed by the operator before release. The plan is a real deliverable — framed as “what we’d implement if we were your agency.” If the prospect converts to a retainer, the plan migrates into the Client Context Engine as their active strategy.

Plan lifecycle in the portal

generating → pending_strategy_review → pending_detail_review → approved → released

Only "approved" and "released" plans are visible in the portal.
If no plan is ready, the portal shows a placeholder: “a bespoke 6-week marketing plan, built for you.”

Portal plan features

  • View — plan intro, week-by-week breakdown with tasks, rendered via PlanView component.
  • Activate — self-run activation. Creates task progress tracking rows for every task in every week. Sets activation_path = "self_run".
  • Task tracking — toggle individual tasks as complete/incomplete after activation. Each toggle updates six_week_plan_task_progress.
  • Revision request — client can submit a revision note (minimum character count enforced via settings). One revision per plan. The note is stored on the plan row and a review task is enqueued.
  • Revision reply — when the operator resolves the revision, the reply is shown to the client with a dismiss action.
  • PDF download — via /api/lite/portal/plan/[planId]/pdf. Generates a branded PDF using an HTML template rendered through Puppeteer. PDFs are cached in memory with a configurable TTL.
PDF generation pipeline
renderPlanPdf(planId, contactId)
  └ Check plan exists + status is "approved" or "released"
  └ Check in-memory cache (keyed by planId + generation_version)
  └ If miss: build HTML via buildPlanPdfHtml()
  └ Render to PDF via renderToPdf() (Puppeteer)
  └ Cache result, log download activity
  └ Return { buffer, filename, generationVersion }

The PDF filename is branded: the output comes from planPdfFilename() which incorporates the company name.

Section 09

Referral System

The portal includes a lightweight referral mechanism. At milestone moments (determined by a cooldown timer), the portal shell shows a ReferralPrompt — a non-intrusive prompt asking if the client knows someone who could use SuperBad’s services.

Flow

1. Milestone check: shouldShowMilestonePrompt(contactId)
   → Check last_referral_prompt_at_ms on contact
   → If null or past cooldown → show prompt

2. Client responds: clicks "Refer" → ReferralForm opens
   → Fields: name, email, optional note

3. Submit: submitReferral()
   → Create company from email domain (or fallback name)
   → Create deal via createDealFromLead() with source = "referral"
   → Link deal to referrer (company + contact)
   → Log activity on both sides (referrer + referred)
   → Insert bartender “Thanks — we’ll reach out” chat message
   → Generate LLM follow-up email draft (if LLM enabled)

4. Dismiss: sets last_referral_prompt_at_ms = now (starts cooldown)

Follow-up email generation

When LLM calls are enabled, the system auto-generates a warm follow-up email to the referred person. The prompt enforces SuperBad’s voice: dry, direct, no jargon, no hard sell. The opening line always references the referrer by name as social proof. If the referrer included a note, it is woven into the email naturally.

Section 11

Portal Lifecycle

Entry paths

Clients enter the portal through different paths. All paths converge on the same portal experience, but the welcome screen adapts:

Trial Shoot Prospect
  Magic link in journey email → redeem → welcome (bypassed) → chat home
  Sees: chat, gallery, plan, deliverables, Brand DNA

Direct/Referral Retainer Client
  Magic link in welcome email → redeem → welcome screen
  Shows “what we already know” from company notes
  → Brand DNA gate → complete assessment → full portal

SaaS Subscriber
  Magic link in onboarding email → redeem → welcome screen
  Generic welcome without pre-populated summary
  → onboarding sequence (segmentation, credentials) → portal

Welcome screen

The welcome page at /lite/portal/welcome is a one-shot surface. It shows once per contact (tracked via contacts.onboarding_welcome_seen_at_ms). Trial-shoot graduates bypass it entirely — their portal experience is continuous.

The welcome page checks the audience (retainer vs SaaS) and renders accordingly. Retainer clients see a “what we already know” summary drawn from company notes. SaaS subscribers see a cleaner onboarding start.

First-visit flow

Magic link redeemed
  ├ if onboarding_welcome_seen_at_ms === null
  │   → redirect to /lite/portal/welcome
  │   → mark as seen → redirect to /lite/portal/home
  └ else
      → redirect to /lite/portal/home

Retainer kickoff

The first portal visit after a deal is won triggers a special bartender opening line. The kickoffVariant prompt acknowledges the new chapter, references the first invoice if one is pending, and surfaces first-shoot scheduling as the single next action. After delivery, retainer_kickoff_bartender_said_at_ms is set on the contact so the kickoff never repeats.

Bundle hub intercept

When deliverables become ready (detected by the presence of a Cloudinary gallery folder on the deal), the portal shows the bundle hub on next visit — a two-card layout linking to the gallery and the 6-week plan. The hub is one-shot: clicking either card sets bundled_hub_seen_at_ms and the normal chat home resumes on future visits.

60-day non-converter archival

Non-converting prospects (trial-shoot completers who don’t become retainer clients) retain portal access for 60 days after shoot completion. The plan tracks this via portal_expiry_email_sent_at_ms (warning email) and portal_archived_at_ms (archive date). An optional extension is possible via portal_extended_until_ms.

After the 60-day window:

  • The portal archives — read-only or locked.
  • The Brand DNA prose portrait remains accessible as a PDF takeaway.
  • Chat is no longer available.
  • The 6-week plan stays as a standalone reference document.
Implementation Status

The archived portal mode is defined in the type system but not yet fully wired. The getPortalMode() function currently returns pre_retainer for non-converters. The 60-day archival logic, expiry emails, and read-only archive view are logged as future work.

Subscription cancel flow

SaaS subscribers can access a cancel/pause flow at /lite/portal/subscription. The page handles three branches:

  • Paused — subscriber has already paused; shows current state.
  • Pre-term — within a commitment period; shows exit math (remainder, buyout cost) and alternative products/tiers.
  • Post-term — past commitment; shows tier up/down options and product switching before confirming cancellation.

The flow is gated by the saas_cancel_flow_enabled kill switch. When disabled, a fallback message directs the subscriber to get in touch directly.

Section 12

Implementation Tips

  1. Build auth first. The magic link → cookie → guard chain is the foundation. Every portal page depends on requirePortalSession(). Get this working end-to-end with a real email send before touching anything else.
  2. Keep portal auth separate from admin auth. Clients never log into an admin session. The two cookie systems coexist on the same domain without interference. Do not try to unify them.
  3. Token security matters. Store only the SHA-256 hash, never the raw token. Mark tokens as consumed on redemption. Set real TTLs. The recovery form must give the same response regardless of whether the email exists.
  4. Mode gating is server-side. Never trust the client to hide locked sections. The server components check getPortalMode() and render SectionLocked for pre-retainer users. No data leaves the server for locked sections.
  5. The bartender prompt is the product. The chat system’s value comes from the system prompt, the context assembly, and the voice constraints. The code is plumbing. Spend your prompt iteration budget here.
  6. Rate-limit LLM calls aggressively. Daily chat limits, cached opening lines, and idempotent generation checks all exist to prevent runaway API costs. Never call the LLM on a page refresh if the output already exists.
  7. Escalation creates real inbox threads. When the bartender escalates, it creates a real thread in the operator’s unified inbox. This is not a log entry — it is a first-class message that expects a response. Build the inbox integration early.
  8. One-shot flags are cheap insurance. The welcome screen, bundle hub, kickoff line, and tour all use timestamp columns on the contacts table. Set them to Date.now() on first occurrence. Check for null to determine if they should fire. Simple, reliable, no race conditions.
  9. The gallery is just a Cloudinary folder. No separate media table, no upload pipeline on the portal side. The operator sets cloudinary_gallery_folder on the deal, and the portal reads from it. Keep it that simple.
  10. PDF generation is expensive. It spins up Puppeteer to render HTML to PDF. Cache the result in memory with a TTL. Never regenerate on every download. The cache key should include the plan’s generation_version so cache invalidation happens automatically on plan regeneration.
  11. Task progress is toggleable. Plan tasks flip between complete and incomplete. The completed_at_ms field alternates between a timestamp and null. This is intentional — people change their minds.
  12. Test the recovery flow. Sessions expire. Cookies get cleared. Mobile browsers are hostile to httpOnly cookies. The recovery flow is the safety net — it must work flawlessly or clients get permanently locked out.
  13. Brand DNA gate is retainer-only. Pre-retainer users can explore freely. Only paying retainer clients are hard-gated behind Brand DNA completion. This is a deliberate design choice: you gate people who are committed, not people who are exploring.
  14. Motion is part of the product. The portal uses a house spring (stiffness: 300, damping: 30) for all transitions. The gate, hub, chat, and menu all animate with Framer Motion and respect prefers-reduced-motion. If a state change doesn’t animate, something is missing.
