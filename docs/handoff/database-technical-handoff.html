Section 01

System Overview

SuperBad Lite runs on a single SQLite database file in WAL mode, accessed through Drizzle ORM with better-sqlite3 as the driver. The entire platform — CRM, billing, content studio, AI infrastructure, client portal — shares one database file, one connection pool, and one schema barrel export.

This is a deliberate architectural choice. SQLite eliminates network latency to a database server, simplifies deployment to a single process, and makes backups trivial (Litestream streams WAL frames to Cloudflare R2 in real time). The trade-off is single-writer concurrency, which is fine for a solo-operator agency platform that processes requests sequentially.

DATABASE ARCHITECTURE
---------------------

API Routes        -->  Drizzle  /data/superbad.db (prod)

One file. 248 tables. No connection strings. No network hops. Just a file on disk with a write-ahead log.

Section 02

SQLite & WAL Mode

The database connection is established in lib/db/index.ts. It uses better-sqlite3 (a native Node.js addon) for synchronous access, wrapped by Drizzle ORM for type safety. Two PRAGMA directives are set immediately on connection:

lib/db/index.ts
import Database from "better-sqlite3";
import { drizzle } from "drizzle-orm/better-sqlite3";
import * as schema from "./schema";

const databaseUrl = process.env.DATABASE_URL ?? "file:./dev.db";

const sqlite = new Database(filePath);
sqlite.pragma("journal_mode = WAL");    // Write-Ahead Logging
sqlite.pragma("foreign_keys = ON");     // Enforce FK constraints

export const db = drizzle(sqlite, { schema });

Why WAL Mode?

Write-Ahead Logging (WAL) is the recommended journaling mode for SQLite in server applications. Instead of writing changes directly to the database file and maintaining a rollback journal, WAL appends changes to a separate -wal file. This gives you:

  • Concurrent readers. Readers don't block writers and writers don't block readers. Multiple server components can read simultaneously while the scheduled-tasks worker writes.
  • Better write performance. Writes only need to append to the WAL file, not rewrite pages in the main database file.
  • Crash safety. If the process crashes, SQLite replays the WAL on next open. No data loss for committed transactions.
  • Streamable backups. Litestream watches the WAL file for new frames and replicates them to R2 in near-real-time without stopping the database.

Global Singleton Pattern

The database connection is cached on globalThis in development to survive Next.js hot module reloading (HMR). Without this, every HMR cycle would open a new connection, eventually exhausting file handles:

lib/db/index.ts — singleton guard
const globalForDb = globalThis as unknown as {
  __sblite_sqlite?: Database.Database;
};

const sqlite =
  globalForDb.__sblite_sqlite ?? new Database(filePath);

if (process.env.NODE_ENV !== "production") {
  globalForDb.__sblite_sqlite = sqlite;
}

In production, a new connection is created per process start (there's only one). In development, the same connection is reused across HMR cycles.

Why Foreign Keys Matter

SQLite disables foreign key enforcement by default. The foreign_keys = ON pragma is essential — without it, cascading deletes and referential integrity checks are silently skipped. Every onDelete: "cascade" and onDelete: "set null" in the schema depends on this pragma being active.

Section 03

Drizzle ORM Layer

Drizzle is a TypeScript-first ORM that generates SQL at build time rather than using a query builder at runtime. The key selling point: your schema files are your type definitions. When you define a column as text("tier", { enum: DISCOUNT_TIERS }), Drizzle infers both the SQL DDL and the TypeScript type from the same declaration.

Schema-as-Types Pattern

Every schema file exports three things:

  1. The table definition — a sqliteTable() call that defines columns, constraints, and indexes.
  2. The select type — typeof table.$inferSelect, representing a row as read from the database.
  3. The insert type — typeof table.$inferInsert, representing the shape needed to insert a new row (optional columns are optional in the type).
lib/db/schema/sequences.ts — typical pattern
import { sqliteTable, text, integer } from "drizzle-orm/sqlite-core";

export const sequences = sqliteTable("sequences", {
  name: text("name").primaryKey(),
  current_value: integer("current_value").notNull().default(0),
});

export type SequenceRow = typeof sequences.$inferSelect;
// { name: string; current_value: number }

Enum-as-Const Pattern

TypeScript enums are avoided throughout the codebase. Instead, every enumerated value is defined as a const array and passed to Drizzle's text() column with an enum option:

Enum pattern used everywhere
export const WEBHOOK_RESULTS = ["ok", "error", "skipped"] as const;
export type WebhookResult = (typeof WEBHOOK_RESULTS)[number];

// Used in schema:
result: text("result", { enum: WEBHOOK_RESULTS }).notNull(),

This gives you: runtime array for validation/iteration, TypeScript union type for compile-time checks, and SQLite TEXT column with Drizzle-enforced constraints. The same array can be used in API validation (Zod), UI select options, and database queries.

JSON Columns

SQLite stores JSON as TEXT. Drizzle's { mode: "json" } option automatically serialises on write and parses on read:

JSON column pattern
payload: text("payload", { mode: "json" }).notNull(),
// TypeScript type: unknown
// SQLite storage: TEXT containing JSON string
// Drizzle handles JSON.stringify on write, JSON.parse on read

The Barrel Export

lib/db/schema/index.ts re-exports every schema file (110 export lines). This single import is passed to Drizzle at connection time via import * as schema from "./schema", enabling Drizzle's relational query API to resolve joins across the entire schema graph.

Drizzle-Kit for Migrations

drizzle.config.ts at the project root points Drizzle-Kit at the barrel export and the migrations folder. Running npx drizzle-kit generate diffs the TypeScript schema against the existing migrations and produces a new .sql file. The platform applies these automatically at boot via instrumentation.ts.

Index Strategy

The schema defines 370 indexes across all tables. The indexing strategy follows two rules:

  1. Composite indexes lead with the filter column. index("activity_log_company_idx").on(t.company_id, t.created_at_ms) supports both "all events for company X" and "all events for company X after date Y" queries efficiently.
  2. Every foreign key has an index. SQLite doesn't auto-create indexes on FK columns (unlike PostgreSQL). Without explicit indexes, cascading deletes do table scans.

370 indexes for 248 tables. About 1.5 per table. Enough to make queries fast, not so many that writes suffer.

Section 05

Migration System

Migrations live in lib/db/migrations/ as numbered SQL files. There are 100 migration files spanning from 0000_init.sql (the initial schema) through 0099_add_intro_funnel_instagram_handle.sql. The system uses Drizzle-Kit's journal-based migration tracking.

How Migrations Run

Migrations are applied automatically at server boot via Next.js's instrumentation.ts hook. This means zero manual migration commands in production — deploy the code and the database schema updates itself:

instrumentation.ts — boot sequence
export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    if (process.env.NEXT_PHASE !== "phase-production-build") {
      const { runMigrations } = await import("./lib/db/migrate");
      runMigrations(dbUrl);
    }
    // ... Sentry init, worker start
  }
}

The NEXT_PHASE !== "phase-production-build" guard is critical. During next build, Next.js imports server modules to collect page data. Running migrations during build would fail because the production database isn't available. The guard skips migrations during build and only runs them at actual server start.

The Migration Runner

lib/db/migrate.ts does three things in sequence:

  1. Drizzle migrations. Reads the journal in migrations/meta/_journal.json, applies any un-applied SQL files via drizzle-orm/better-sqlite3/migrator.
  2. Seed files. Any SQL file in the migrations folder that isn't tracked in the journal (convention: seed files like 0001_seed_settings.sql) is executed. These use INSERT OR IGNORE for idempotency.
  3. Admin user seed. Ensures the admin user (andy@superbadmedia.com.au) exists with the correct password hash. If ADMIN_PASSWORD is set in the environment, updates the hash if it changed.
Migration Best Practice

Never modify an existing migration file. If you need to change a table, create a new migration. The journal tracks which files have been applied by filename; editing an applied migration corrupts the state. Drizzle-Kit handles this automatically when you run npx drizzle-kit generate.

Generating a New Migration

  1. Edit the schema file in lib/db/schema/.
  2. Run npx drizzle-kit generate. This diffs the TypeScript schema against the existing migrations and creates a new .sql file.
  3. Review the generated SQL. Drizzle-Kit is generally good but sometimes generates unnecessary statements.
  4. The migration applies automatically on next server start.
drizzle.config.ts
export default {
  schema: "./lib/db/schema/index.ts",
  out: "./lib/db/migrations",
  dialect: "sqlite",
  dbCredentials: {
    url: process.env.DATABASE_URL ?? "file:./dev.db",
  },
} satisfies Config;
Section 06

Scheduled-Tasks Worker

The scheduled-tasks worker is the platform's deferred execution engine. Every feature that needs to do something later — send an email in 3 days, check for overdue invoices, generate a cockpit brief at 8am, run the lead-gen daily search — inserts a row into scheduled_tasks and the worker picks it up when it's due.

Worker Architecture

WORKER LOOP (1-minute interval)
-------------------------------

1. Kill-switch check
   -> If scheduled_tasks_enabled is OFF, write heartbeat, return 0

2. Reclaim stale
   -> Any row with status="running" for >15 min: reset to "pending"
   -> Covers worker crashes mid-processing

3. Pull batch
   -> SELECT up to 50 rows WHERE status="pending" AND run_at_ms <= now

4. Process each
   -> Atomic claim: UPDATE status="running" WHERE status="pending"
   -> Dispatch to handler by task_type
   -> Success: status="done", done_at_ms=now
   -> Failure: attempts++, exponential backoff

5. Sweep overdue invoices
   -> Piggybacks on every tick (separate from task queue)

6. Write heartbeat
   -> Upsert worker_heartbeats with tick timestamp + tasks processed

Task Lifecycle

StatusMeaningNext Transition
pendingWaiting for its run_at_ms timeWorker claims it → running
runningCurrently being processedSuccess → done, Failure → back to pending with backoff
doneCompleted successfullyTerminal
failedExhausted all 3 attemptsTerminal
skippedDeliberately not executedTerminal

Failure & Retry

The worker uses exponential backoff with a base of 5 minutes and a multiplier of 6:

  • Attempt 1 fails: retry in 5 min x 6^1 = 30 minutes
  • Attempt 2 fails: retry in 5 min x 6^2 = 3 hours
  • Attempt 3 fails: status = failed (terminal)

This is deliberately aggressive. If a task fails 3 times with hours between attempts, something is structurally wrong. Manual triage is needed.

The idempotency_key column has a unique index. Features use this to prevent duplicate task scheduling. For example, manual_invoice_generate uses deal:{deal_id}:cycle:{cycle_number} as its key. If you try to schedule the same invoice generation twice, the unique constraint rejects the duplicate.

Kill-Switch System

Every feature that can spend money, send email, or hit an external API autonomously is gated by a kill switch. The switches are defined in lib/kill-switches.ts as a typed registry with compile-time enforcement: if you add a feature that calls an external service without gating it behind a switch, you're breaking the autonomy protocol.

How Kill Switches Work

lib/kill-switches.ts — usage pattern
import { killSwitches } from "@/lib/kill-switches";

// In any feature handler:
if (!killSwitches.outreach_send_enabled) {
  return { skipped: true };
}

The registry ships with all switches defaulting to their safe state. Switches that gate autonomous outreach, content sending, and monitoring default to false (off). Switches for core infrastructure like scheduled_tasks_enabled and llm_calls_enabled default to true because the platform doesn't function without them.

Section 08

Settings Registry

Kill switches are the on/off gates. The settings registry is the fine-tuning knobs. Every autonomy-sensitive threshold, interval, cap, and configuration value lives in the settings database table and is accessed through a typed registry in lib/settings.ts.

Architecture

SETTINGS FLOW
-------------

docs/settings-registry.md     (source of truth -- all keys documented)
        |
        v
seed migration                 (INSERT OR IGNORE into settings table)
        |
        v
lib/settings.ts                (typed registry with Zod validation)
        |
        v
settings.get("key")            (in-memory cache -- DB lookup -- Zod parse)
        |
        v
Feature code reads value       (never uses literal constants)

The critical design constraint: feature code must never use literal constants for autonomy-sensitive values. Instead of writing if (days > 30), you write if (days > await settings.get("portal.non_converter_archive_days")). An ESLint rule enforces this boundary.

How the Registry Works

lib/settings.ts — typed read
const registry = {
  "finance.gst_rate": decimal,
  "portal.non_converter_archive_days": integer,
  "lead_generation.daily_max_per_day": integer,
  "warmup.week_one_cap": integer,
  // ... 190+ keys
};

// Usage in feature code:
const gstRate = await settingsRegistry.get("finance.gst_rate");
// TypeScript knows this is a number. Type-safe all the way down.

The registry uses Zod schemas to validate and coerce stored values. The settings table stores everything as TEXT strings; the registry transforms them to the correct runtime type (number, boolean, parsed JSON array, enum).

In-Memory Cache

Settings are cached in a Map after first read. The cache is invalidated on write via settings.set(). This avoids hitting the database on every settings read (which happens hundreds of times per request in a platform with 190+ configurable thresholds).

Settings Domains

Adding a New Setting

Four steps, always in order: (1) Add the row to docs/settings-registry.md. (2) Add the INSERT OR IGNORE to a seed migration. (3) Add the key + Zod schema to lib/settings.ts. (4) Use settings.get("key") in feature code. Skip any step and something breaks silently.

Table Design

lib/db/schema/activity-log.ts — table definition
export const activity_log = sqliteTable("activity_log", {
  id: text("id").primaryKey(),
  company_id: text("company_id").references(() => companies.id, {
    onDelete: "cascade",
  }),
  contact_id: text("contact_id").references(() => contacts.id, {
    onDelete: "set null",
  }),
  deal_id: text("deal_id").references(() => deals.id, {
    onDelete: "cascade",
  }),
  kind: text("kind", { enum: ACTIVITY_LOG_KINDS }).notNull(),
  body: text("body").notNull(),
  meta: text("meta", { mode: "json" }),
  created_at_ms: integer("created_at_ms").notNull(),
  created_by: text("created_by"),
});

The FK references are nullable because not every event belongs to a company, contact, or deal. Platform-level events (cost anomalies, cockpit briefs, admin sessions) only set the relevant FK. The meta JSON column carries structured data specific to each kind — for example, a stage_change event stores { from: "lead", to: "contacted" }.

Four composite indexes cover the common query patterns: events by company, by contact, by deal, and by kind. All are compound with created_at_ms for time-range filtering.

Section 10

Monitoring & Observability

The platform has four observability layers, each serving a different audience and time horizon.

1. Sentry (Error Tracking)

Sentry is configured across three runtimes: server (Node.js), client (browser), and edge. All three are gated by the sentry_enabled kill switch. When the switch is off (the default), the beforeSend callback returns null to suppress all events:

sentry.server.config.ts
Sentry.init({
  dsn: process.env.SENTRY_DSN,
  tracesSampleRate: killSwitches.sentry_enabled ? 0.15 : 0,
  beforeSend(event) {
    if (!killSwitches.sentry_enabled) return null;
    return event;
  },
});

The sampling rate is 15% when enabled. This is enough to catch patterns without burning through Sentry's event quota on every request.

2. PostHog (Analytics)

PostHog captures user interactions on admin and portal surfaces. It's a client-side SDK (posthog-js) that auto-captures page views and custom events. The data feeds into retention analysis and feature adoption metrics.

3. Cost & Usage Observatory

The platform's own cost monitoring system, built around three database tables:

TablePurpose
external_call_logEvery API call with estimated AUD cost. The raw ledger.
cost_anomaliesDetected spikes from 3 detectors (hard threshold, rate of change, learned band).
band_overridesRuntime adjustments to per-job cost ceilings and learned-band multipliers.

Three anomaly detectors run on a scheduled cadence:

  1. Hard threshold: fires if a single call or daily total exceeds a configured ceiling.
  2. Rate detector: fires if the rate of spending accelerates beyond a configured multiplier.
  3. Learned band: builds a rolling 7-day average and fires if the current value exceeds the band multiplier.

Anomalies are tiered (low / mid / severe) and carry an acknowledgement lifecycle. Severe anomalies can auto-trigger kill switches to halt runaway spending.

4. Worker Heartbeat

The simplest monitor: the scheduled-tasks worker writes a timestamp to worker_heartbeats on every tick (1 minute). The admin cockpit renders a red health banner if the last heartbeat is more than 5 minutes old. If the banner shows, the worker has stopped.

OBSERVABILITY STACK
-------------------

Sentry      -> Errors & traces      (gated by kill switch)
PostHog     -> User analytics        (client-side auto-capture)
Observatory -> API cost monitoring   (3 detectors, 3 tiers)
Heartbeat   -> Worker health         (1-minute cadence, admin banner)

Environment & Boot Sequence

Environment Validation

Environment variables are validated at boot via a Zod schema in lib/env.ts. If any required variable is missing or invalid, the server refuses to start with a clear error message listing every issue:

lib/env.ts
const envSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
  NEXT_PUBLIC_APP_URL: z.url(),
  NEXTAUTH_URL: z.url(),
  NEXTAUTH_SECRET: z.string().min(1).optional(),
  DATABASE_URL: z.string().min(1).default("file:./dev.db"),
  ADMIN_EMAIL: z.string().email().default("andy@superbadmedia.com.au"),
  ADMIN_PASSWORD: z.string().min(1).optional(),
});

const parsed = envSchema.safeParse(process.env);
if (!parsed.success) {
  throw new Error(`[env] SuperBad Lite refused to boot...`);
}

This runs at the end of instrumentation.ts via await import("@/lib/env"). The fail-loudly pattern means you never get a running server with missing config — you get a clear crash with a list of what's wrong.

Boot Sequence

The instrumentation.ts file defines the complete server boot sequence. On the Node.js runtime (not edge, not build):

BOOT SEQUENCE (instrumentation.ts -- register())
--------------------------------------------

1. Set AUTH_TRUST_HOST=true (if not already set)

2. Run database migrations
   -> Drizzle journal migrations
   -> Seed SQL files (INSERT OR IGNORE)
   -> Admin user seed (create or update password)

3. Import Sentry server config
   -> Sentry.init() with kill-switch-gated sampling

4. Start scheduled-tasks worker
   -> 1-minute poll interval
   -> Handler registry loaded from lib/scheduled-tasks/handlers

5. Bootstrap lead-gen daily search
   -> Ensure the daily search task is enqueued

6. Validate environment variables (lib/env.ts)
   -> Zod schema parse
   -> Fail-loud on missing/invalid vars
Build-Time Guards

Steps 2, 4, and 5 are wrapped in NEXT_PHASE !== "phase-production-build" guards. During next build, Next.js imports instrumentation to discover route metadata. Running migrations or starting a worker during build would crash. The guards skip all side-effects during build and only execute at actual server start.

Implementation Tips

When adding a new table: Create the schema file in lib/db/schema/, re-export it from index.ts, run npx drizzle-kit generate to create the migration, and restart the dev server (migrations auto-apply).

When adding a new scheduled task type: Add the type to the SCHEDULED_TASK_TYPES array in scheduled-tasks.ts, register the handler in lib/scheduled-tasks/handlers/, and export it from the handler barrel file.

When adding a new activity log kind: Add the kind to the ACTIVITY_LOG_KINDS array in activity-log.ts. The type system auto-infers the new kind in all consumers.

When querying across tables: Use Drizzle's relational queries or manual joins. The full schema graph is available because the barrel export passes * as schema to the drizzle() constructor.

One SQLite file, 248 tables, 370 indexes, 87 task types, 400 log kinds, 190 settings, 27 kill switches. All in a single Next.js process. Sometimes boring tech is the superpower.
