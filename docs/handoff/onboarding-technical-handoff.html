Section 01

What the Onboarding System Does

The Onboarding System is a composition layer that takes two very different kinds of paying customers — retainer clients who pay thousands per month for hands-on marketing and SaaS subscribers who self-serve for $19–$897/month — and walks them both through a structured sequence that ends with a complete Brand DNA profile, an authenticated portal account, and enough data for the platform to work on their behalf from day one.

There are two distinct paths, with a shared core:

  • Retainer path (4 steps): Welcome → Brand DNA Assessment → Practical Setup → Credential Creation
  • SaaS path (5 steps): Welcome → Brand DNA Assessment → Revenue Segmentation → Product Config → Credential Creation

Brand DNA is a hard gate. No client or subscriber gets product access until they complete the ~30 minute personality assessment. This is a deliberate quality decision, not an oversight — the platform is better because every user has a full profile.

There is also a third entry path: the Trial Shoot via the Intro Funnel. Trial shoot prospects are not “onboarded” in the traditional sense — they go through a separate funnel (landing page → questionnaire → payment → booking → shoot → deliverables → reflection) and only enter the retainer or SaaS onboarding path if they convert.

Two audiences, one promise: by the time you reach the product, we already know who you are.

Section 02

Architecture

The Orchestrator Pattern

The onboarding system owns no state table. Instead, it reads from the primitives it composes — Brand DNA profile status, Revenue Segmentation timestamps, wizard completion records, user credential state — and derives the current step at read time. This is a thin orchestration layer, not a state machine.

getOnboardingState(companyId, audience) → OnboardingState

  Reads:
    brand_dna_profiles.status           → is Brand DNA complete?
    companies.revenue_segmentation_completed_at_ms → Rev Seg done? (SaaS only)
    wizard_completions                   → practical setup done? (retainer only)
    user.emailVerified                   → credentials created?
    contacts.onboarding_welcome_seen_at_ms → welcome screen shown?

  Returns:
    { currentStep, completedSteps, totalSteps, audience }

Entry Points

AudienceTriggerWhat Happens
Retainer Quote accepted via Quote Builder Deal → Won, welcome email + portal token generated, onboarding nudges scheduled
SaaS Stripe payment success Company + contact auto-created, welcome email sent, onboarding nudges scheduled
Trial shoot Section 1 form submit on /trial-shoot Enters Intro Funnel — separate flow, may convert to retainer/SaaS later

Portal Auth Model

First visit:  /portal/[token]  → token-based access, no login needed
                                  → token authenticates the session for onboarding

Final step:   Credential creation  → "Confirm your email — this is how you'll log in"
                                     → magic link email sent → first authenticated login

After that:   /portal  → standard Auth.js magic link authentication
                       → token-based URL redirects to standard auth

Tokens are single-use for initial authentication, scoped to one client, and expire after 30 days if unused. No passwords anywhere. Magic link only via Auth.js v5.

Retainer Onboarding Flow

The retainer flow is deeper and more personal. Every retainer client enters via quote acceptance — no alternative trigger. This means the system always has deal context, quote details, and sales conversation history to personalise with.

The 4-Step Journey

Entry-Path Branching

Not all retainer clients see the welcome screen. Trial-shoot graduates who convert to retainer bypass the welcome screen entirely — their portal experience is continuous, and a fresh “welcome to SuperBad” interstitial would break the lived continuity.

Detection Logic

Trial-shoot graduate = a row exists in intro_funnel_submissions for this contact’s company. Direct/referral = no such row. The welcome screen only renders for direct/referral entrants.

The “What We Already Know” Paragraph

This is the highest-leverage creative moment in the onboarding spec. An Opus LLM call reads deal notes, quote context, and outreach research — all unstructured data — and synthesises a warm, observant paragraph that makes the client feel known before the assessment starts. If it’s generic or wrong, the welcome screen fails.

On Stripe payment success, the system creates a company and contact record in a single transaction. Solo operators who skip the business name field get their full name as the company name — the record exists so Revenue Segmentation and location data always have a home on companies.

Section 05

Trial Shoot Flow

The trial shoot is SuperBad’s primary customer acquisition surface. A $297 on-site photography/video shoot that functions as both a lead qualifier and a relationship builder. The experience lives in the Intro Funnel — a separate system from onboarding proper, but a critical feeder into it.

The 12-Stage Funnel State Machine

contact_submitted         Section 1 form → deal created at Trial Shoot stage
  ↓
questionnaire_in_progress  Shape-branched questions, one per screen
  ↓
questionnaire_complete     "Pay now & book" card activates
  ↓
paid                       Stripe Payment Element, cinematic reveal
  ↓
shoot_booked               Native calendar, 5-day advance + 3/week cap
  ↓
shoot_approaching          48h out — automatic transition
  ↓
shoot_morning_of           Day of the shoot
  ↓
shoot_completed_awaiting_deliverables
  ↓
deliverables_ready         Gallery + six-week plan both approved → bundled release
  ↓
reflection_complete        8-question self-persuasion arc + Claude synthesis
  ↓
portal_dormant             60 days post-shoot, then archive
  ↓
portal_archived_migrated   Won → migrated to full client portal

Key Design Details

  • 60 minutes on-site only. No studio variant in v1.
  • A bespoke six-week marketing plan is included as a deliverable alongside the photo/video output.
  • Reschedule is free up to 48h before the shoot. Inside 48h, the booking is lost (extenuating circumstances case-by-case).
  • Deliverables are bundled — gallery and six-week plan must both be ready before the portal flips. Whichever lands second fires the transition.
  • Non-converter portal lifecycle: 60 days of access post-shoot-completion, then the portal archives. The six-week plan PDF is emailed one last time. Cloudinary gallery media persists.

Shape-Branched Questionnaire

A single branching dimension drives the questionnaire variant: solo_founder / founder_led_team / multi_stakeholder_company. Three variants across 4 sections yield 12 question banks. The shape is captured at Section 1 submit and written to both the submission snapshot and the canonical companies.shape column.

Retainer-Fit Recommendation

After the reflection questionnaire, Claude Opus generates a structured recommendation: retainer / saas / neither / either_strong with confidence level and reasoning. This surfaces in the Daily Cockpit for Andy’s review — never shown to the prospect.

intro_funnel_retainer_fit columns
recommendation_type: "retainer" | "saas" | "neither" | "either_strong"
confidence:          "high" | "medium" | "low"
reasoning_text:      string   // Opus-generated reasoning
flags_json:          JSON     // structured concern flags
drift_check_passed:  boolean  // brand-voice check on the reasoning
Section 06

Setup Wizards

Every integration, configuration, and multi-step setup task in the platform runs through a shared wizard shell. No raw forms. No self-serve config panels. Every setup is hand-held, step-by-step, with save-and-resume, a completion ceremony, and a typed completion contract.

Shell Architecture

WizardShell (routing, save-resume, progress, cancel, audience tone)
  └── Wizard instance (specific wizard: Stripe, Cloudinary, Brand DNA, etc.)
       └── Step instance (one screen in the wizard)
            └── Step type (form | oauth-consent | api-key-paste | webhook-probe |
                        dns-verify | csv-import | async-check | content-picker |
                        review-and-confirm | celebration | custom)

Wizard Definition Shape

TypeScript — WizardDefinition
type WizardDefinition<TCompletionPayload> = {
  key: string;                    // 'stripe-admin', 'onboarding-segmentation', etc.
  audience: 'admin' | 'client';
  renderMode: 'slideover' | 'dedicated-route';
  steps: WizardStepDefinition[];
  completionContract: CompletionContract<TCompletionPayload>;
  vendorManifest?: VendorManifest;
  voiceTreatment: {
    introCopy: string;
    outroCopy: string;
    tabTitlePool: TabTitlePool;
    capstone?: CapstoneConfig;
  };
};

Two Rendering Modes

ModeWhen UsedBehaviour
slideover Default for integrations + configs Parent surface behind with backdrop blur, 60% width desktop, 100% mobile
dedicated-route Flagship flows: Brand DNA, Onboarding, Intro Funnel Full-page takeover at the wizard’s canonical URL

Audience Tone Switching

One shell, two personalities. The audience prop drives spacing (compact vs generous), copy register (terse vs branded), celebration intensity (quiet check vs cinematic motion), and sprinkle eligibility.

Completion Contract

The shell refuses to mark a wizard complete without the required artefacts. The contract declares which keys must be present in the payload, runs a real verify() call against the vendor, and specifies which database rows must exist. If verification fails, the step rewinds and shows a branded error message.

Save-and-Resume

Auto-saves every step. Deep-link resume URLs. A wizard_progress row tracks the in-flight state. 24h email nudge for abandoned wizards. 30-day expiry with a day-29 warning. Non-resumable steps (like OAuth consent) rewind to the last safe step.

Three wizards must complete in fixed order on first admin sign-in: Stripe → Resend (email) → Graph API (mailbox). They run as one continuous arc. The capstone moment after the third wizard: “SuperBad is open for business.”

Section 07

Revenue Segmentation

A structured short questionnaire capturing business-stage data for upsell targeting. SaaS-only — retainer clients do not complete it (they’re already in a direct relationship).

Five Questions

#QuestionOptionsColumn
Q1 Monthly revenue Under $250K / $250K–$500K / $500K–$1M / $1M–$3M / $3M+ revenue_range
Q2 Team size Just me / 2–5 / 6–15 / 16–50 / 50+ team_size
Q3 Biggest constraint 6 plain-spoken options (e.g. “Not enough of the right customers”) biggest_constraint
Q4 12-month goal 5 options: steady / grow / scale / launch new / figure out twelve_month_goal
Q5 Industry vertical 8 broad categories + Other with free-text industry_vertical

All five answers are stored as columns directly on the companies table. No separate table, no JSON blob. This is deliberate — Revenue Segmentation data is queried alongside company records for upsell filtering, and denormalising it avoids joins in every pipeline query.

Upsell Targeting Layer

Revenue Segmentation feeds a two-tier upsell model evaluated by evaluateUpsellTier(companyId):

TierCriteriaSurface
Warm Revenue $500K+ OR logged in 10+ of last 14 days. Must match location gate. Pipeline “Upsell candidates” filter
Hot Revenue $500K+ AND high engagement (10+ login days + 3+ features) AND goal = scale/launch. Must match location gate. Daily Cockpit alert

All thresholds read from settings.get() — no hardcoded values. The location gate defaults to Victoria, Australia and is configurable for geographic expansion.

Section 08

Get-Started Funnel

The get-started funnel is not a single page — it’s the constellation of public-facing entry points that feed into the onboarding system. Three surfaces converge on the same eventual outcome: a paying customer entering the onboarding sequence.

Three Entry Surfaces

SurfaceURLWhat It Does
Trial Shoot Landing /trial-shoot Editorial landing page → contact form → questionnaire → Stripe payment → calendar booking. The warm acquisition path.
Free Audit Tool /get-started/audit Business name + URL → automated enrichment pipeline → graded A–F scorecard with branded PDF report. Creates a warm lead with auto-drafted follow-up referencing their weakest score.
SaaS Product Pages /products/[slug] Interactive demo + pricing comparison → checkout with Stripe Payment Element → onboarding triggers on payment success.

SaaS Checkout Shape

SaaS checkout uses an anti-conventional pricing model. Three commitment cards framed around identity, not discounts:

  • Getting started (monthly) — same per-month price + one-time setup fee
  • Committed (annual, monthly-billed) — same per-month price, no setup fee, 12-month commitment
  • All in (annual, upfront) — pay the full year, no setup fee

The setup fee on every new monthly subscription naturally closes the cancel-and-resubscribe loophole. No anti-gaming logic needed.

Free Audit Tool → Pipeline

The audit tool creates a deal via createDealFromLead(source: 'audit_tool') immediately — no manual step. The auto-drafted follow-up email leads with the customer’s weakest category, not a generic pitch. The prospect also receives a branded PDF report (cover page, scorecard, per-category recommendations, earned soft CTA on the final page).

Abuse Protection

IP rate limit (3 audits per 24h) + invisible Cloudflare Turnstile + honeypot field. Each audit costs ~$0.15–$0.30 in API calls, so abuse protection is about cost, not just security.

Section 09

Nudge Scheduling

Two nudge systems run in parallel: onboarding nudges (for non-starters and abandoned Brand DNA) and practical setup reminders (for retainer clients who haven’t completed their admin tasks). Both use the platform’s shared scheduled_tasks worker.

Onboarding Nudge Cadence

AudienceCadenceBehaviour
Retainer Single nudge at 24h One automated reminder. After that, cockpit flag for Andy — personal follow-up territory.
SaaS 24h → 72h → weekly Escalating automated chain. Self-re-enqueuing — the handler schedules the next nudge when it fires.

Self-Re-Enqueueing Pattern

Nudge handlers are defensive: they re-read onboarding state at fire time and skip if the target step is already complete. When they do send, they enqueue the next nudge in the chain using the scheduled_tasks enqueue primitive with an idempotency key that prevents double-scheduling.

lib/onboarding/schedule-nudges.ts
async function scheduleOnboardingNudges(input: {
  contactId: string;
  companyId: string;
  audience: "retainer" | "saas";
}): Promise<void> {
  if (!killSwitches.onboarding_nudges_enabled) return;

  const delayHours = audience === "retainer"
    ? await settings.get("onboarding.retainer_non_start_nudge_hours")
    : await settings.get("onboarding.saas_nudge_first_hours");

  await enqueueTask({
    task_type: "onboarding_nudge_email",
    runAt: Date.now() + delayHours * 60 * 60 * 1000,
    payload: { contactId, companyId, audience, nudgeIndex: 0 },
    idempotencyKey: `onboarding_nudge_${contactId}_0`,
  });
}

Practical Setup Reminders

Retainer-only. Per-step targeting — the reminder only mentions the steps that are actually incomplete. Three wizard keys are tracked: practical-contact-details, practical-ad-accounts, practical-content-archive. Cadence: 24h → 72h → weekly until all three are done.

Nudge Email Tone

  • SaaS nudges reference progress if they started: “You’re 40% through Brand DNA — pick up where you left off.”
  • Practical setup reminders are brief and specific: “Quick one — we still need your Meta Business Manager access. Takes about 2 minutes.”
  • Never guilt. Never “your subscription is active but you haven’t started.”
  • All nudge emails classified as transactional — bypass the outreach quiet window.

Kill Switches

Both nudge types are gated by onboarding_nudges_enabled. If flipped off, all scheduling and sending silently stops. The wizard resume nudge (wizard_resume_nudge) is a separate system owned by the Setup Wizards spec.

Section 11

Integration with Other Systems

The onboarding system is a composition layer — it touches almost every major subsystem in the platform. Here is how each connection works.

Brand DNA Assessment

Direct composition. The onboarding orchestrator routes to Brand DNA as a step. Brand DNA handles save/resume, the reveal, and retake independently. The onboarding system reads brand_dna_profiles.status and is_current to determine if the gate has been passed. Crucially, the gate checks for an existing completed profile, not whether Brand DNA was done during this onboarding flow — a contact who completed Brand DNA during a trial shoot skips it on retainer conversion.

Sales Pipeline + Quote Builder

Quote acceptance is the retainer onboarding trigger. The handleQuoteAccepted event fires the entire sequence: welcome email, portal token generation, nudge scheduling. Pipeline provides companies.location for retainer clients and the upsell filter (“Warm” and “Hot” subscribers) surfaces as a standing filter on the pipeline board.

SaaS Subscription Billing (Stripe)

Stripe payment success triggers SaaS onboarding. The OnboardingDashboardClient component handles four subscription states: active (shows Brand DNA CTA), at_cap (tier upgrade hero), past_due (card update with SetupIntent), and waiting (Stripe confirmation pending). Tier changes are handled via applyTierChange() with upgrade-only enforcement from the subscriber surface.

Daily Cockpit

Consumes: new Hot upsell candidate alerts, stalled onboarding counts (retainer + SaaS), incomplete practical setup flags, Brand DNA retake notifications. The cockpit is the primary surface for Andy to monitor onboarding health across all clients and subscribers.

Client Management Portal

The portal is where the welcome screen and Brand DNA assessment render. The welcome screen (/portal/welcome) marks onboarding_welcome_seen_at_ms on first view. The portal also hosts the Brand DNA retake nudge card (12-month threshold).

Email System (Resend)

All onboarding emails route through sendEmail() with classification: 'transactional'. Welcome emails are Claude-drafted with brand-voice drift checking. Nudge emails use static templates with personalisation tokens.

LLM Pipeline (Claude Opus)

Three LLM calls in the onboarding flow, all routed through the model registry via invokeLlmText():

  • onboarding-welcome-email — generates the welcome email (subject + body HTML)
  • onboarding-welcome-summary — generates the “what we already know” paragraph for retainer welcome screens
  • intro-funnel-retainer-fit — generates the retainer-fit recommendation after reflection

Section 12

Implementation Tips

  1. Start with the orchestrator, not the UI. getOnboardingState() is the foundation. Build and test the step-derivation logic against real database states before touching any frontend. The orchestrator is a pure read function — no side effects, easy to unit test.
  2. The Brand DNA gate is non-negotiable. Every path through the code must enforce it. If you find yourself writing a “skip Brand DNA” escape hatch, stop. The only exception is the dev-mode bypass (BRAND_DNA_GATE_BYPASS=true) for local development.
  3. Derived state means no state table — but also no single point of truth. The onboarding state is reconstructed on every read from 5+ different tables. This is architecturally clean but means edge cases can emerge (e.g. Brand DNA marked complete but portrait generation failed). The orchestrator checks for actual completion conditions — status = 'complete' AND completed_at_ms IS NOT NULL — not just a status flag.
  4. Token-based portal access is the bridge between anonymous and authenticated. The first visit uses a URL token. The last step creates a real Auth.js user. The tricky part is the transition: the token session must persist through the entire onboarding flow, then the credential creation step issues a magic link that establishes a proper Auth.js session. Make sure token expiry doesn’t race with slow completers.
  5. Nudge handlers must be defensive. Always re-read the onboarding state at fire time. The customer may have completed the step in the 24 hours since the nudge was scheduled. The scheduled_tasks idempotency key prevents double-scheduling, but the handler itself must validate that the nudge is still relevant.
  6. Welcome email generation is an Opus API call per signup. At scale, this is real cost. The llm_calls_enabled kill switch gates it — if disabled, generateWelcomeEmail() returns null and the caller should fall back to a static template. Build the fallback from day one.
  7. Revenue Segmentation columns are on companies, not a separate table. This was a deliberate design decision to avoid joins in every pipeline query. If you need to add more segmentation questions later, add columns to the companies table following the same enum pattern. Don’t reach for a JSON blob.
  8. The upsell targeting layer reads from settings.get() for every threshold. No hardcoded values. This means you can tune thresholds post-launch without a deploy. Test with different settings values — the defaults are educated guesses.
  9. Practical setup wizards are independent. They can be completed in any order. The nudge system sends per-step reminders — only mentioning the steps that are actually incomplete. Build each wizard as a standalone unit, then wire them into the orchestrator’s practical-setup check.
  10. Client-facing surfaces say “SuperBad”, never “SuperBad Lite”. Lite is the internal/admin name. This applies to welcome emails, portal titles, step preview copy, nudge emails, and every other customer-visible string. The browser tab titles are specified: “SuperBad — welcome, [First Name]”, “SuperBad — almost there”, etc.
The Biggest Risk

Brand DNA as a 30-minute hard SaaS gate is the biggest bet. If 60% of paying subscribers abandon during the assessment, that’s a real problem. The mitigation is that Brand DNA is designed to be engaging, not boring — but it’s still 30 minutes before product access. Monitor signup-to-completion rates and adjust the assessment experience if abandonment is too high — but don’t remove the gate.
