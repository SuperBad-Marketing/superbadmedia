Section 01

What the Admin Dashboard Does

The Admin Dashboard is the single operator’s command centre. One person — Andy, the solo founder of a Melbourne marketing business — runs everything through this surface: sales pipeline, client management, content production, finances, lead generation, hiring, and daily planning. Every admin page lives under /lite/admin/* or /lite/cockpit.

The Daily Cockpit (/lite/cockpit) is the default morning surface. It aggregates signals from every other system into a single-screen briefing: an AI-written daily narrative, a list of things waiting on the operator, system health warnings, today’s calendar, and a kanban-style task planning board. Three AI briefs a day — morning, midday, evening — watch the business unfold in the operator’s own dry, observational voice.

Beyond the cockpit, the admin surface spans ~20 pages covering Pipeline, Clients, Lead Gen, Proposals, Campaigns, Briefs, Content, Hiring, Products, Finance, Invoices, Inbox, Tasks, Calendar, Settings, and an Observatory (system observability). Every page wraps in a shared AdminShellWithNav component that provides a sidebar, animated navigation, a bottom nav for mobile, and a persistent braindump FAB.

One person runs a marketing business through a single browser tab. The cockpit’s job is to make sure that person always knows what matters right now.

Section 02

Architecture

Application Structure

SuperBad Lite is a Next.js App Router application. The admin area consists of two route groups: app/lite/admin/* (pipeline, clients, settings, etc.) and app/lite/cockpit/* (daily cockpit, health, waiting). Both wrap their children in the same AdminShellWithNav component.

app/lite/admin/
  layout.tsx      ── AdminShellWithNav + EggOrchestrator + event toasts
  page.tsx         ── redirects to /lite/admin/pipeline
  pipeline/       ── sales pipeline (kanban board)
  clients/        ── client list & detail
  lead-gen/       ── outreach queue + verticals manager
  proposals/      ── proposal builder
  campaigns/      ── campaign management
  briefs/         ── production briefs
  hiring/         ── contractor hiring pipeline
  products/       ── SaaS product management
  invoices/       ── invoice list & actions
  settings/       ── admin settings
  errors/         ── error log viewer
  contacts/[id]/  ── contact detail & context
  companies/[id]/ ── company detail
  deals/[id]/     ── deal detail & call prep

app/lite/cockpit/
  layout.tsx      ── AdminShellWithNav + event toasts
  page.tsx        ── the daily cockpit (main surface)
  actions.ts      ── regenerate brief, toggle habits
  health/         ── full health banner list
  waiting/        ── full waiting-items list

Auth Pattern

Every admin page runs its own auth() check server-side and redirects to /lite/login if the user is not an admin. The shell layouts never enforce auth themselves — they’re pure chrome. This means each page is independently testable and independently deployable.

Data Flow

Page (RSC) ──→ Server queries ──→ DB (SQLite + Drizzle)
     │
     ├──→ Aggregator ──→ mergeWaitingItems() / mergeHealthBanners()
     │                      ↳ parallel Promise.allSettled across all source specs
     │
     ├──→ Brief Generator ──→ LLM (Claude via model registry)
     │
     └──→ Client Components ──→ Framer Motion + houseSpring

The cockpit page fetches seven data sources in parallel using Promise.all: the current brief, waiting items, health banners, calendar events, task kanban, today’s braindump status, and today’s habits. Each source is fault-isolated — if one fails, the others still render.

Section 03

Daily Cockpit

What Andy Sees

The cockpit is the first thing the operator sees each morning. It’s a single-column layout (max-width 720px) with six zones stacked vertically:

  1. Greeting header — time-of-day greeting (“Morning.” / “Afternoon.” / “Evening.”) plus a rotating tagline from a pool of 6 dry one-liners. Changes daily by day-index modulo.
  2. AI narrative brief — hero card with 2–3 sentences in SuperBad’s voice. The brief tells Andy what’s happening, what’s stuck, and what needs him.
  3. Habits panel — daily routine checklist with streak tracking, optimistic UI toggles, and flame icons for active streaks.
  4. Braindump section — quick capture entry point (or confirmation if already done today).
  5. Attention rail — horizontal chip row of up to 6 “waiting on Andy” items, sorted by urgency. Overflow links to /lite/cockpit/waiting.
  6. Health banners — conditional. Only renders when something is broken. Up to 2 visible, overflow to /lite/cockpit/health.
  7. Calendar preview — today’s bookings (shoots, meetings) with time-ordered chips.
  8. Planning view — kanban board (Must Do / Should Do / If Time) with a list-view toggle. Mobile uses a tabbed interface with animated transitions between columns.

Two floating action buttons sit in the corners: an AI chat FAB (bottom-left) for conversational queries against the platform, and a braindump FAB (bottom-right) for quick brain dumps from any admin surface.

Three Daily Briefs

SlotMelbourne TimePurpose
morning06:00Orientation — state of the business, what today looks like
midday12:00Progress check — what’s moved, what’s stuck
evening18:30Day wrap + tomorrow preview — how the day closed

Brief Generation Pipeline

1. Determine slot (morning/midday/evening) from Melbourne wall-clock time
2. Check kill switches: cockpit_briefs_enabled + llm_calls_enabled
3. Gather context in parallel:
     ├── mergeWaitingItems()
     ├── mergeHealthBanners()
     ├── getTodayCalendarEvents()
     └── getAndyFacingActivitySince(slotStart)
4. Quiet-slot check: if zero items + zero banners + zero events → skip
5. Load prior briefs: midday reads morning; evening reads morning + midday
6. Build prompt (slot-specific template with all context injected)
7. Invoke LLM via invokeLlmText({ job: "cockpit-brief", ... })
8. Upsert result into cockpit_briefs table
9. Log activity (generated / regenerated / skipped)

Chained Continuity

Each brief’s prompt includes the prior briefs from the same day. The morning brief gets today’s raw signals. The midday brief gets the morning’s prose plus an event trail since 6 AM. The evening brief gets both prior briefs, the full day’s event trail, and tomorrow’s calendar. The prompts explicitly instruct: “reference earlier briefs if useful, but don’t invent continuity.”

Event Trail

The function getAndyFacingActivitySince() queries the activity_log table for a curated allow-list of 25 event kinds that are relevant to the operator: task completions, quote acceptances, invoice payments, subscription state changes, outreach replies, intro funnel bookings, content publications, hiring events, and more. Capped at 50 events to keep the prompt within token budget.

Material-Event Regeneration

When a significant business event fires (deal won, payment failed, large invoice paid), the source spec calls maybeRegenerateBrief(eventKey). This helper debounces via a scheduled_tasks check (configurable debounce window in minutes) and enqueues a cockpit_brief_regenerate task. The regeneration replaces the cached brief for the current slot.

Material Event Denylist

Events that trigger brief regeneration: subscription_payment_failed, subscription_cancelled, invoice_paid_large, outreach_reply_positive, intro_funnel_booking_confirmed, deal_won, deal_lost, graph_api_token_expired, graph_api_subscription_lapsed, cost_anomaly_detected.

Section 04

Health Banners

What They Are

Health banners are system-level warnings that something is broken or degrading across the platform. They surface on the cockpit as a strip of up to 2 coloured banners — red for critical, orange for warning. Overflow links to a dedicated /lite/cockpit/health page showing all active issues.

Banner Shape

TypeScript — HealthBanner Interface
interface HealthBanner {
  id: string;
  severity: "warning" | "critical";
  summary: string;       // single-line human description
  href: string;          // tap-through to the relevant admin page
  source: string;        // which system flagged it (e.g. "task_manager")
}

Banner Sources

The aggregator (lib/cockpit/aggregator.ts) calls Promise.allSettled across 8 source functions in parallel. If any source throws, the others still report:

SourceFunctionExample Trigger
Task ManagergetTaskHealthBanners()5+ overdue tasks → critical
ObservatorygetObservatoryHealthBanners()External API anomalies
SaaS ProductsgetSaasHealthBanners()Headline metric degradation
HiringgetHiringHealthBanners()Stale candidate applications
FinancegetFinanceHealthBanners()Cost anomalies
InboxgetInboxHealthBanners()Graph API token expiry
ContentgetContentHealthBanners()Content queue stalls
WizardsgetWizardHealthBanners()Integration setup failures

Sort Order

Banners sort by severity (critical first), then alphabetically by ID for stability. The cockpit shows at most 2; the health page shows all.

Severity Escalation

The task manager example: 1–4 overdue tasks = warning. 5+ overdue tasks = critical. Each source defines its own escalation thresholds. There’s no shared severity config — it’s per-source business logic.

Section 05

Task Management

Task Model

Tasks are the core planning primitive. Every task has a kind, status, priority, optional due date, optional entity link (to a contact or company), and an optional checklist.

DimensionValues
Kindspersonal, admin, prospect_followup, client_deliverable, client_task
Statusestodo → in_progress → blocked / awaiting_approval → delivered / done / cancelled
Prioritieshigh, normal, low
Recurrencesdaily, weekly, biweekly, monthly, quarterly, yearly

Cockpit Kanban Columns

The cockpit’s planning view sorts tasks into three columns based on due date and priority:

Column Logic (lib/tasks/cockpit.ts)
// Must Do:
if (due < todayStart)                         // overdue
if (due is today && priority === "high")       // due today + high priority

// Should Do:
if (due is today && priority !== "high")       // due today + normal/low

// If Time:
if (due is this week && priority === "high")  // upcoming + high priority

Approval Workflow

Tasks of kind client_deliverable support a client-facing approval flow. The task moves to awaiting_approval status with a one-time approval token. The client can approve or reject with feedback. Approved/rejected timestamps and feedback are stored on the task row. Pending approvals surface as waiting items on the cockpit’s attention rail.

Braindump Integration

Tasks can originate from the braindump system. The source_braindump_id column tracks provenance. Braindump-created tasks are indexed for fast lookup.

The cockpit’s calendar preview shows today’s active bookings in time order. Each event displays as a time + type label chip (“10:00 AM Shoot”). The empty state: “Nothing on the calendar today. Unscheduled time is underrated.”

The evening brief prompt additionally receives tomorrow’s calendar via getTomorrowCalendarSummary(), so it can warn about early morning shoots or dense days.

Section 07

Brain Dump

Concept

The braindump is a quick-capture surface. Andy types raw text — tasks, content ideas, script concepts — and an LLM parses it into structured items. The parsed items go through a review screen where Andy can adjust kind, priority, due date, and entity links before committing them into the task and content systems.

Access Points

  • Braindump FAB — floating action button in the bottom-right corner, visible on every admin surface. Pulses once if not used today (controlled by localStorage date tracking). Keyboard shortcut: Cmd+Shift+D.
  • Cockpit section — inline braindump card on the cockpit. Shows a prompt if not done today (“Morning brain. Go.”), or a summary with stat pills if already committed (tasks created, posts suggested, scripts drafted).

Parse → Review → Commit

Raw text ──→ LLM parse (parseBraindumpAction)
               │
               ↓
         Structured items
         ├── ParsedTask[]      (kind, title, priority, due, entity)
         ├── ParsedContentIdea[] (type, caption, notes)
         └── ParsedScriptIdea[]  (pillar, format, hook, notes)
               │
               ↓
         Review UI (edit kind, priority, dates, entity links)
               │
               ↓
         commitBraindumpAction() ──→ insert tasks + content + scripts

Database Record

Each braindump creates a braindumps row storing the raw text, surface context (which page triggered it), LLM parse timestamp, commit timestamp, and count of each created item type. A braindump with committed_at_ms set is considered “done” for today’s cockpit display.

Section 08

Unified Inbox

What It Does

The Unified Inbox (/lite/inbox) aggregates messages across channels (email, Instagram DMs, SMS, etc.) into a single three-column desktop layout. The left column contains view/address/sort controls, the middle column lists threads, and the right column shows thread detail with conversation history.

URL-Driven State

The inbox is fully server-driven via URL search params:

URL Shape
/lite/inbox?view=focus&address=all&thread=<id>&sort=recent
  • view — focus (needs attention), all (everything), sent (outbound)
  • address — filter by connected email/channel address, or all
  • sort — recent (newest first), oldest, unread
  • thread — selected thread ID for the detail panel

Key Features

  • Compose modal with contact picker (searches existing contacts)
  • Customer context panel in thread detail — shows the contact’s company, pipeline stage, and relevant context
  • Sync actions for pulling in new messages from connected channels
  • Cleanup modal for bulk archiving old threads
  • Mobile layout collapses to a single-column thread list with a dedicated mobile thread detail view
  • Offline banner detecting connectivity loss

Cockpit Integration

The inbox contributes waiting items to the cockpit’s attention rail via getInboxWaitingItems() (unread threads needing response) and health banners via getInboxHealthBanners() (Graph API token expiry, sync failures).

Nav Item Shape

TypeScript — AdminNavItem
type AdminNavItem = {
  id: string;             // unique identifier
  label: string;          // display text
  href: string | null;    // null = disabled/coming soon
  icon: LucideIcon;       // Lucide React icon component
  status: "live" | "soon";  // "soon" renders muted + aria-disabled
  matchPrefix: string | null; // for active-state resolution
}

Active-State Resolution

The matchActiveId() function resolves which nav item is active by matching the current usePathname() against each item’s matchPrefix. Longest prefix match wins, so /lite/admin/pipeline beats /lite/admin.

Animated Active Bar

The active nav item gets a 3px pink vertical bar on its left edge. This bar is a shared Framer Motion layoutId="admin-nav-active-bar", so when the route changes, the bar animates between items using the house spring. All nav items are wrapped in a LayoutGroup to enable this shared animation.

House Spring
// The platform-wide spring config from lib/design-tokens.ts
export const houseSpring = {
  type: "spring",
  stiffness: 300,
  damping: 30,
  mass: 1,
};

Reduced-motion users get an instant reposition (duration: 0) without breaking layout.

Mobile Bottom Nav

On viewports below md (768px), the sidebar hides and a fixed bottom navigation bar appears. It shows 5 priority items: Cockpit, Pipeline, Inbox, Tasks, Settings. Uses the same matchActiveId() function and nav data structure as the sidebar.

Global Search

A GlobalSearchTrigger component sits between the primary and utility nav groups. It opens a search overlay for finding contacts, companies, deals, and tasks across the platform.

Profile Chip

Pinned to the bottom of the sidebar: Andy’s name, role badge (“admin” in the brand accent colour), and a link to settings.

Premium Finish Requirement

Every admin page must use the AdminShellWithNav layout, brand font/colour tokens, a display heading, the breadcrumb/eyebrow pattern, and a narrative tagline. No generic Tailwind styling on page chrome. This is enforced at the project level — spec says “pages must have the premium finish.”

Easter Egg System

Philosophy

SuperBad Lite runs a hidden “surprise & delight” system inspired by Metal Gear Solid’s fourth-wall breaks. The platform notices patterns in the operator’s behaviour and occasionally surfaces dry, observational commentary. 80% ambient platform-awareness in a closed list, 20% hidden MGS-style “the platform has been watching” moments. Maximum frequency: once per month per egg.

Suppression Gates

Hard gates that prevent any egg from firing, regardless of trigger match:

  • Payment element is mounted (Stripe checkout in progress)
  • Email compose is focused
  • Quote acceptance flow active
  • Error page displayed
  • Onboarding wizard active
  • First-ever login (user hasn’t seen the platform yet)
  • Session age under 30 seconds

Cadence System

Two independent cadence controls prevent egg fatigue:

  • Global cadence — configurable via surprise.admin_egg_cadence_per_days setting. No egg fires if the last egg fired within this window.
  • Per-egg cooldown — each egg has its own cooldownDays. Some use Infinity (one-shot, never re-fires). The fired egg ID is tracked in user.fired_egg_ids_recent (JSON array, max 50 entries).

CRT Turn-Off Effect

The most theatrical egg. When triggered, a full-screen overlay plays a 4-phase CRT television shutdown animation:

  1. Dim (300ms) — screen darkens to 70% black
  2. Static (180ms) — SVG fractal noise overlay simulating analogue static
  3. Collapse (600ms) — viewport collapses to a 2px horizontal line with glow, like an old TV powering off
  4. Frozen — black screen with message: “you’ve been up until 2am three nights running. I’m pulling the plug.” and a directive: “close this tab.”

CRT scanlines are layered throughout using a repeating CSS gradient with mix-blend-mode: multiply.

The platform literally turns itself off on you. That’s the joke.

Section 12

Implementation Tips

  1. Start with the aggregator pattern. The cockpit’s mergeWaitingItems() and mergeHealthBanners() use Promise.allSettled to call every source in parallel. If you’re building a dashboard that aggregates data from multiple domains, this fault-isolation pattern is essential — one broken source doesn’t crash the whole page.
  2. The brief generator is a pure function composition. Context gathering, prompt building, and LLM invocation are completely separate concerns. You can test each independently: mock the context, test the prompt template, mock the LLM response.
  3. Quiet-slot detection saves real money. Checking for zero signals before calling the LLM means you’re not paying for “nothing to report” briefs. The static fallback pool handles that for free.
  4. Melbourne wall-clock time is load-bearing. Every time calculation — brief slots, calendar queries, braindump “today” detection, habit completions — uses lib/time/melbourne.ts to convert UTC to local time. If you’re adapting this for a different timezone, centralise the conversion and don’t scatter new Date() calls through your codebase.
  5. The nav data structure is static, not dynamic. Navigation items are a TypeScript array, not fetched from a database. Active-state resolution runs client-side via usePathname(). This means zero network requests for nav state. Add items by editing the array.
  6. Framer Motion layoutId is how the active bar animates. The pink indicator bar has layoutId="admin-nav-active-bar". When the active item changes (route change), Framer Motion automatically animates the bar between positions using the house spring. The entire nav tree must be inside a LayoutGroup for this to work.
  7. Easter eggs are fail-closed. Every trigger function returns null by default. Ambiguous state = no fire. Suppression gates block all eggs during sensitive moments (payment flows, onboarding, first login). Build your delight features the same way — they should never interrupt important user flows.
  8. The egg cadence system prevents fatigue. Global cadence (days since any egg), per-egg cooldown, and a recent-fires list (capped at 50 entries) work together. For your own version, start with the per-egg cooldown and add the global budget later.
  9. Custom events for cross-component communication. Eggs fire on the server but render on the client. The bridge is a window.dispatchEvent(new CustomEvent("admin-egg-fired", { detail })) pattern. Each egg renderer listens for its own eggId. Clean separation: orchestration is server-side, presentation is client-side.
  10. Material-event regen needs debouncing. Without it, 3 quick deal-won events in a row would generate 3 briefs. The scheduled_tasks check with a configurable debounce window (in minutes) ensures at most one regen per burst.
  11. The braindump is an LLM parsing pipeline. Raw text in, structured ParsedTask[] / ParsedContentIdea[] / ParsedScriptIdea[] out, human review step, then commit. Never auto-commit LLM output into your production data. Always give the user a review step.
  12. Optimistic UI on habits. The habits panel uses React 19’s useOptimistic hook. Toggle fires instantly client-side while the server action runs in a transition. If the server action fails, the state reverts. This makes daily check-offs feel instantaneous.
Final Note

The cockpit is an aggregation layer over a dozen independent systems. It composes; it does not duplicate. Every waiting item, every health banner, every calendar event comes from its source spec’s own query function. The cockpit’s only original content is the AI brief — and even that is built from everyone else’s signals. If you’re building something similar, resist the urge to re-derive data at the dashboard level. Let each domain own its own queries.
